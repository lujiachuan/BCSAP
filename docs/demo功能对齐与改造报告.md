# demo 功能对齐与改造报告

> 对象：`demo/argon_tuning/argon_tuning/cluster_control_gui.py`（旧 Tkinter 真机原型）与当前 BCSAP 平台
>
> 范围：手动控制、自动调束、扫谱采集，以及直接影响三者的 PV 映射与执行服务
>

## 1. 结论

当前迁移并不是简单复制 demo：新平台已经建立客户端、仪器执行服务、EPICS 适配器、设备组锁、状态机和本地持久化，基础架构明显强于旧版。

但从实验功能对齐程度看：

| 模块 | 当前结论 |
|---|---|
| 手动控制 | 主体设备控制和紧凑单页布局基本完成；缺少磁铁成组设定、全局只读模式，设备安全限值编辑链路不完整。**（本轮已修：成组设定 §8.9 P2.1、全局只读 §8.9 P2.2、安全字段回写 §8.3 第 1 行）** |
| 自动调束 | 已有可运行的 GP+EI、人工确认、真实写入和结构化记录；缺少原 demo 的两阶段策略、束流丢失回退、束线拓扑、配置持久化和完成后处置。**（本轮已修：白名单与拓扑 §8.6 第 1 行、启动前快照与束流丢失回退 §8.6 第 2 行、完成后处置 §8.6 第 3 行、两阶段策略 §8.6 第 4 行、配置持久化与响应曲线/建议/日志 §8.9 P2.3–P2.4；连续自动写入仍按 §9 P2.5 留给现场安全评审）** |
| 扫谱 | 已有平台自执行的通用逐点磁铁扫描；原 demo 的 LabVIEW/MSScan 采集链路尚未接入，导出与回落功能存在未完成和错误实现。**（本轮已修：逐路到位 §8.4、服务端回落 §8.4、终态竞态 §8.4、导出语义与文件名 §8.5、协议冻结 §8.3 第 6 行；LabVIEW/MSScan 接入仍待现场回答冻结文档 §10 的 7 个问题）** |

当前最需要优先处理的不是视觉样式，而是以下四项正确性问题：

1. 设置页保存 PV 映射会丢失安全字段。
2. 成组扫描只验证第一路磁铁，无法确认其余磁铁是否到位。
3. 扫描回落只写第一路磁铁，界面中的回落速率没有真正下发。
4. 扫描终态存在内存状态与数据库状态短暂不一致的竞态。

## 2. 原 demo 的实际能力

`cluster_control_gui.py` 是上过真机的集成程序，不是纯界面原型。它由四个页签组成。

| 页签 | 主要能力 |
|---|---|
| 手动控制 | FC1/FC2 实时读数和趋势；气体、溅射、JM、DW 13 路、BD 5 路、磁铁 4 路控制；磁铁 1+2、3+4、1~4 成组设定；全部关断 |
| 贝叶斯调参 | FC1/FC2 优化目标；按 FC1～FC5 自动勾选上游参数；逐参数后联合微调或全部联合两种策略；束流丢失回退；配置保存；响应曲线；监控建议和日志 |
| 质谱扫描采集 | 启停 LabVIEW TCP 监听；控制 MSScan 起停与参数；控制 VI Run/Abort；接收磁铁电流/皮安表曲线；质量换算；交互绘图；JSON/TXT 导出 |
| 参数上限 | 编辑 DW、BD、磁铁等写入上限，保存到 `limits_config.json`，修改记录追加到 `limits_history.jsonl` |

原 demo 的调束停止和完成行为需要特别说明：

- 正常完成可选择保持最优参数或回安全值。
- 用户停止或异常时保持当前参数，不自动回零；急停依靠“全部关断”。
- 两阶段策略会在束流接近零或相比基线大幅下降时恢复前一快照并重试。

### 2.1 demo 自身不能照搬的问题

1. GUI 直接调用 EPICS 写设备，没有统一执行层、设备锁和完整审计。
2. `tuning_logs/*.jsonl` 主要是文本事件，不足以完整复现每一轮数值。
3. `labview_listen.py` 与 `labview_live.py` 可能争写同一个快照文件且结构不同。
4. 通过 SSH/PsExec 后按固定屏幕坐标点击 LabVIEW Run/Abort，分辨率或窗口位置变化就会失效。
5. 某些 IOC 数据库量程与现场使用值不一致，不能直接作为新平台安全边界。
6. demo 的全局“全部关断”并不停止磁铁脉冲，只关闭阀门、溅射、JM、DW 和 BD 输出。

## 3. 当前平台架构

```text
PySide6 客户端
    │ HTTP
    ▼
instrument_service
    ├─ PV 映射与健康检查
    ├─ 统一信号读写、边界/最大单步/速率校验
    ├─ 设备组锁
    ├─ 扫谱状态机与本地暂存
    └─ 调束状态机与逐轮记录
    │ Channel Access
    ▼
EPICS IOC
```

与 demo 相比，当前平台已经实现以下关键改造：

- 客户端不直接导入 EPICS 库，不绕过仪器执行服务写设备。
- 写入统一检查 `min_value`、`max_value`、`max_step` 和 `max_rate`。
- 扫谱与调束使用设备组锁，避免两个任务同时操作共享设备。
- 写入中断导致设备状态未知时进入 `RECOVERY_REQUIRED`，人工确认前保留设备锁。
- 扫谱数据保存为 SQLite 元数据和 NPZ 点列，并记录 SHA-256。
- 调束逐轮保存候选值、实际下发值、实际回读值、目标值和质量状态。

这些能力应继续保留；后续补齐 demo 功能时不能退回 GUI 直连 EPICS 的方式。

## 4. 手动控制对齐情况

### 4.1 已完成

| 能力 | 当前实现 |
|---|---|
| 单页显示 | 不分设备 Tab，按左/中/右三列显示所有设备组 |
| 单设备一行 | 同一设备的设定、回读、开关和脉冲操作合并在一行 |
| 紧凑步进 | 保留 `×1 / ×10 / ×100`，设定框滚轮只修改草稿，必须点“下发”才写设备 |
| 布局调整 | 卡片可拖拽、改变大小、折叠并保存位置；支持恢复默认布局 |
| 实时读数 | FC1/FC2 顶栏读数，设备回读、连接状态和读数滞后提示 |
| 束流趋势 | 30 秒、2 分钟、10 分钟、30 分钟窗口，历史最优线、统计、清空、平移缩放和视图复位 |
| 状态语义 | 设定值与配对回读比较，显示稳定、未稳定、掉线和写入拒绝 |
| 全部关断 | 二次确认后先关闭 toggle 输出，再将连续设定值退到下限或 0；逐项报告拒绝结果 |

### 4.2 仍缺少

#### 磁铁成组手动设定

原 demo 可同时设置磁铁 1+2、3+4、1~4 的电流与速率。当前手动页只有四台磁铁各自一行，没有成组下发。

成组操作不能在客户端循环调用普通单路写接口，否则中途失败会形成部分成功；应在执行服务增加批量校验、批量锁定和明确的部分失败语义。

#### 全局只读监控模式

原 demo 支持 `--read-only`。当前映射可以把单条信号标记为不可写，信号写接口也有 `dry_run`，但客户端没有一个可由部署参数启用的全局只读模式。**（本轮已修：开关放执行服务 `SPECTRUM_READ_ONLY`，写入口全部拒绝 + 四个页面压住入口并说明原因，见 §8.9 P2.2）**

#### 安全限值编辑

原 demo 的“参数上限”页没有形成完整等价功能。当前限值已经进入 `PvMappingEntry`，并由执行服务强制执行，这是正确方向；但系统设置页只编辑设备参数名、业务信号、PV 名、单位、可写和必需。

它没有编辑或只读展示 `group`、`role`、`readback_signal`、边界、变化限制和稳定判据。

更严重的是，设置页保存时只重新组装上述六个字段，会把原配置中的安全字段全部丢掉。保存后可能出现：

- 手动页无法按组和角色正确生成控件；
- 设定与回读失去配对；
- 调束因缺少 `max_step` 被拒绝启动；
- 扫谱因缺少 `settle_tol` 无法判断到位；
- 写入边界和变化速率保护消失。

此问题应在继续接真机前修复。

## 5. 自动调束对齐情况

### 5.1 已完成

| 能力 | 当前实现 |
|---|---|
| 优化器 | 自包含 `GpEiOptimizer`，使用 GP 回归和 EI 采集函数 |
| 真实设备链路 | 候选经执行服务校验后写入设备，等待回读稳定再采目标 |
| 人工确认 | 每轮先显示当前回读、候选值和变化量，操作员确认后执行 |
| 数据记录 | 候选、实际下发、实际回读、目标、质量、算法版本和随机种子结构化保存 |
| 设备互斥 | 调束期间持有参与变量和目标信号所在设备组的锁 |
| 异常恢复 | 写入中断且设备状态未知时保留锁，等待人工确认 |
| 运行监控 | 当前值、历史最优、相对提升、收敛曲线和最佳水平线 |

### 5.2 仍缺少或实现不完整

#### 束线拓扑和变量白名单

原 demo 根据 FC1～FC5 的物理位置自动选择上游参数。当前页把所有 `role=readback` 的只读信号都列为优化目标，也把所有 `role=setpoint` 的可写信号列为候选变量。**（本轮已修：映射加 `tunable`/`beam_target` 标记 + 束线拓扑 + `/control/v1/tuning/catalog`，见 §8.6）**

这意味着气压、电压回读等可能被误选成“最大化目标”，磁铁变化速率等也可能被误选成普通调束变量。应增加受控配置：

- 可作为目标的束流探测信号白名单；
- 可参与调束的设备参数白名单；
- 探测器与束线路径位置；
- 每个目标对应的上游参数集合；
- 禁止组合与联动组合。

#### 两阶段优化策略

当前只有所有选中变量联合优化。原 demo 的“逐参数优化 → 最后联合微调”尚未迁移，相关的每变量调用次数、保持时间和联合范围比例也没有迁移。**（本轮已修，见 §8.6 第 4 行）**

#### 束流丢失保护与回退

当前可以记录目标读取失败或回读未稳定，但不会因为束流接近零、相比基线下降过多或连续异常而自动恢复前一安全快照。**（本轮已修，见 §8.6 第 2 行）**

需要在服务端实现：

1. 启动前保存全部参与变量的实际回读快照和目标基线；
2. 明确定义绝对归零阈值和相对损失阈值；
3. 连续异常计数；
4. 经执行层斜坡恢复快照；
5. 回退失败进入 `RECOVERY_REQUIRED`；
6. 将回退原因和每一路恢复结果写入审计记录。

#### 磁铁成组优化变量

原 demo 可将 1+2、3+4、1~4 当作一个优化维度并同步下发。当前调束页只列出单路磁铁设定信号。该能力也应建立在服务端原子批量动作上。

#### 配置持久化

当前没有保存和恢复已勾选变量及其范围、优化目标、优化策略、最大轮次、稳定超时、采样次数和完成后动作。**（本轮已修：保存/载入/开跑前自动保存到 `%LOCALAPPDATA%\SpectrumPlatform\tuning_config.json`，打开页面自动载回，见 §8.9 P2.3）**

#### 完成后设备状态

当前调束完成时设备停留在最后一轮参数上，最后一轮不一定是历史最优轮。结果页能显示最优轮，但不能：
**（本轮已修，见 §8.6 第 3 行）**

- 应用最优参数；
- 恢复启动前参数；
- 回安全值。

这三种动作需要明确按钮、二次确认、服务端批量执行和完整结果反馈。

#### “初始回读”含义错误

结果表当前把第一轮执行后的回读当作“初始回读”，没有保存调束启动前快照。字段名称与实际含义不一致。**（本轮已修：状态接口回传启动前快照与目标基线，结果页起点与相对提升都改用快照，见 §8.6 第 2 行）**

#### 辅助分析能力

以下 demo 能力仍未迁移：**（本轮已修前三项与高级参数，见 §8.9 P2.4）**

- 每个变量独立的“设定值—目标束流”响应曲线；
- 调束过程启发式建议；
- 调束日志查看和导出；
- 初始采样数、噪声、每变量调用次数、联合范围、回退次数等高级参数。**（噪声与随机种子已开放；「初始采样数」平台不做：第一个候选固定取范围中心，没有随机初始撒点，给开关会误导——如实记录在 §8.9 P2.4 的取舍里）**

#### 连续自动写入

原 demo 会连续自动写设备，当前固定为“建议 → 人工确认”。这是有意的安全收缩，不应直接恢复。只有在目标/变量白名单、束流丢失回退、批量恢复、硬件联锁确认和审计全部完成后，才应评估无人逐轮确认模式。

## 6. 扫谱对齐情况

### 6.1 当前已经实现的平台扫描

| 能力 | 当前实现 |
|---|---|
| 扫描轴 | 单路磁铁 1～4，以及 1+2、3+4、1~4 成组轴 |
| 执行方式 | 服务端逐点斜坡写磁铁，等待回读稳定，读取 FC1/FC2 |
| 采样 | 每点多次采样取中位数，记录目标值、实际坐标、时间和质量 |
| 质量处理 | 未稳定点可记录并标记，不静默当作正常点；不合格点不画入主曲线 |
| 绘图 | 电流/质量切换、多项式系数、平移、滚轮缩放、复位、十字读数、峰值标注、Y 轴范围、PNG 导出 |
| 持久化 | SQLite 任务元数据、NPZ 点列、原子发布、SHA-256 |
| 停止语义 | 安全停止等待当前点收尾，部分有效数据尽力保存 |

这是一套由 BCSAP 执行服务直接驱动磁铁的通用扫描方式，不等同于原 demo 的 LabVIEW/MSScan 工作流。

### 6.2 原 LabVIEW/MSScan 链路尚未迁移

当前平台没有接入：

- `labview_listen.py` 的启动、停止和状态检测；
- TCP 8904→8905 数据链路；
- `latest_labview.json` 剖面快照；
- 采集批次清空；
- MSScan BooleanStart/BooleanStop；
- StartA、StopA、Rate、WaitStep、WaitTime 的设定与回读；
- RunVI/AbortVI 控制。

这些 MSScan/Scanz PV 虽然列入了模拟 IOC 补充清单，但没有进入平台默认 PV 映射，当前扫谱页也没有使用它们。

迁移时建议将 LabVIEW 数据接收做成仪器执行服务中的独立适配器，输出统一的实时点流和任务状态；不要让 GUI 启动监听脚本、轮询共享 JSON 文件或执行像素点击。

### 6.3 LabVIEW/TCP 采集可靠性改造要求

这部分不能只做到“界面能看到曲线”。谱图是实验原始数据，TCP 接收、批次识别、持久化和任务完成必须形成一条可验证的数据链路。

#### 6.3.1 demo 当前已经处理的内容

`labview_listen.py` 已针对现场数据做过以下修补：

- LabVIEW 发送的是连续 JSON 数组，没有换行，单次 `recv(65536)` 不等于一帧；监听器会保留块尾残片，与下一块拼接后提取跨块的 X/Y 对象。
- LabVIEW 会反复发送“从扫描起点到当前点的完整缓冲”；监听器用 X 值去重，新值覆盖同一 X 的旧值。
- 内存中的剖面每 0.5 秒生成一次 `latest_labview.json`，通常先写 `.tmp` 再 `os.replace()`。
- GUI 读取的是快照文件，不直接处理 TCP 字节流。

这些做法解决了最初“每个网络块只取最后一点”和部分跨块丢点问题，但还没有解决完整的数据可靠性问题。

#### 6.3.2 demo 当前仍存在的丢点和混批风险

1. **TCP 没有应用层帧边界**：TCP 只保证有序字节流，一次发送可能被拆成多次接收，多次发送也可能在一次接收中粘连。正则匹配只能适配当前固定的 `X` 后紧跟 `Y` 格式，不能证明收到了一帧完整 JSON。
2. **中继断连时直接丢数据**：`tcp_relay_config.ps1` 在目标电脑未连接时仍读取 LabVIEW 上行字节，但不会缓存或补发。只有 LabVIEW 后续再次全量发送时才可能恢复；若扫描已经结束，缺失尾段无法自动找回。
3. **原子写失败后退化为直接覆盖**：监听器多次 `os.replace()` 失败后会直接打开正式 JSON 文件覆盖。读进程可能在写到一半时读取，得到截断 JSON。
4. **固定 `.tmp` 文件存在并发竞争**：TCP 处理线程和 reset 监视线程都能调用快照写入，并共用同一个临时文件名。两个写入交错时可能覆盖彼此或替换错误版本。
5. **解析残片是全局变量**：多个连接或断线重连可能把上一连接的半个对象与下一连接的字节拼在一起。新连接必须拥有独立解析器状态，连接结束时丢弃未完成帧。
6. **扫描批次靠 X 回跳猜测**：只有新批次起点比旧剖面最小值低 3 A 以上才清空。新扫描使用相同起点、更高起点、反向扫描或局部重扫时，旧点可能残留并混入新谱图。
7. **按浮点 X 精确去重不可靠**：相同目标点若实际电流有微小抖动，会形成多个近邻键；真正重复测量又会被无提示覆盖。应按 `point_index` 或带容差的扫描坐标处理。
8. **按 X 排序会丢失采集顺序**：反向扫描、回扫和重复点无法从最终 `profile` 恢复真实时间顺序。
9. **最后一批可能没有刷盘**：快照限频为 0.5 秒，连接断开和扫描停止时没有强制最终写入。内存里新增的尾部点可能还没进入 `latest_labview.json`，此时导出会少点。
10. **`seq` 不是可靠点序号**：它累计每次从全量重发帧中提取到的点，包含大量重复，不能用于判断唯一点数、缺口或断线恢复是否完整。
11. **存在两个不兼容写入者**：`labview_listen.py` 写 `profile[]`，`labview_live.py` 写 `history[]`，两者都指向 `latest_labview.json`。必须保证同一数据文件只有一个所有者。**（本轮取证修正：实际是三个——`cluster_control_gui.py:2992-2999` 在点"开始采集"时会直接覆盖成空 `profile` 并删掉 `.tmp`，走的是正常操作路径；另外 `labview_live.py` 写的快照没有 `profile` 键，GUI 读到就是"无数据"。）**
12. **监听所有网卡且允许多个客户端**：`0.0.0.0:8905` 接受并发连接，当前内存剖面却是全局共享，多个发送源会混在一起，也缺少来源校验。

因此，`latest_labview.json` 不能继续作为唯一事实数据源。它最多只能作为可丢弃、可重建的界面快照。

#### 6.3.3 推荐的数据协议

优先与 LabVIEW 端约定应用层帧格式。可选方案按推荐顺序为：

1. 4 字节网络序长度前缀 + UTF-8 JSON；
2. 每帧一行的 NDJSON；
3. 如果 LabVIEW 端暂时不能修改，接收器实现真正的增量 JSON 数组解析，并把每次完整数组视为一帧。

每帧建议至少包含：

```json
{
  "protocol_version": 1,
  "run_id": "MS-20260914-001",
  "frame_seq": 37,
  "sent_at": "2026-09-14T10:30:21.123+08:00",
  "axis": "dipole_current",
  "detector": "picoammeter",
  "units": {"x": "A", "y": "nA"},
  "full_snapshot": true,
  "point_count": 1520,
  "points": [
    {"index": 0, "x": 40.0, "y": 0.012, "sampled_at": "..."}
  ],
  "checksum": "..."
}
```

关键字段的作用：

- `run_id` 明确区分扫描批次，不再根据 X 值猜测新扫描。
- `frame_seq` 用于识别重复帧、乱序帧和缺失帧。
- `point.index` 保留原始采集顺序，允许反向扫描和重复坐标。
- `full_snapshot` 明确这一帧是完整快照还是增量点。
- `point_count` 和 `checksum` 用于发现截断、内容损坏和不完整终帧。
- `sent_at` 与接收端 `received_at` 同时保存；顺序与超时判断使用单调时钟，审计时间使用带时区时间戳。

所有数值必须验证为有限数，限制单帧字节数、最大点数和字段长度，异常帧只记录错误，不能拖垮接收服务。

#### 6.3.4 接收与断线恢复

接收器应位于 `instrument_service` 或独立采集服务中，并满足：

- 每条 TCP 连接拥有独立缓冲区和解析状态；不得使用跨连接全局残片。
- 只允许一个受信来源写入一个活动 `run_id`；第二连接应拒绝或进入明确的备用状态。
- 使用有界队列将网络读取与数据库写入解耦；队列接近上限时报警，不能静默丢点。
- 连接中断时把任务标记为 `DATA_INTERRUPTED`，保留已接收点和断点序号。
- 重连后只接受同一 `run_id` 的更高 `frame_seq`；全量帧可用于校验和补齐，增量帧必须检查连续性。
- 如果中继仍然保留，至少记录连接断开区间和丢弃字节数。更可靠的中继需要按完整帧缓存并重放，而不是对裸字节流做无缓冲转发。
- 接收循环结束、收到扫描停止、Run 完成或进入超时时，必须执行一次强制落盘，不能只依赖 0.5 秒定时快照。
- 断线后的半帧必须丢弃；不能与新连接数据拼接。

如果 LabVIEW 只能持续发送全量剖面，新服务应把每个更高 `frame_seq` 的完整剖面视为版本化快照：先完整校验，再用它补齐当前任务；校验失败时保留上一个已确认版本。

#### 6.3.5 持久化与 `latest_labview.json`

推荐的数据分层是：

```text
TCP 帧
  → 帧校验
  → 任务内追加记录/版本化快照
  → SQLite 元数据 + 临时点文件
  → 完成时原子发布 NPZ
  → UI 增量接口
  → latest_labview.json（可选诊断快照）
```

原始接收数据应先进入任务存储，UI 和导出都从任务存储读取。这样即使快照文件被覆盖，也不会丢失已经确认的谱图点。

如果为了兼容旧工具继续生成 `latest_labview.json`，必须遵守：

- 只有一个进程拥有写权限；禁止 `labview_live.py` 和监听器同时写。
- 每次使用同目录唯一临时文件，写入后 `flush + fsync`，最后 `os.replace`。
- 原子替换失败时保留旧快照并报警，绝不能回退为直接覆盖正式文件。
- 快照包含 `run_id`、`snapshot_seq`、唯一点数、最后点序号、生成时间和完整性校验。
- GUI 先检查 `run_id` 和 `snapshot_seq`，只接受更新版本；解析失败时继续显示上一有效版本并提示快照异常。
- 快照是完整当前视图，不是唯一历史记录；覆盖是允许的，因为历史点已经持久化在任务存储中。

#### 6.3.6 扫描生命周期和完成判据

建议增加独立的 LabVIEW 扫描状态机：

```text
IDLE → ARMED → RUNNING → DRAINING → FINALIZING → COMPLETED
                         └──────────────→ FAILED / RECOVERY_REQUIRED
```

- `ARMED`：创建 `run_id`、保存设备与实验元数据快照、确认监听就绪后才触发 MSScan。
- `RUNNING`：接收数据并持续记录帧序号、唯一点数、最后数据时间和连接状态。
- `DRAINING`：收到停止/完成信号后继续等待最后完整帧，不能立即按当前快照结束。
- `FINALIZING`：核对终帧点数、序号连续性、校验值和设备停止状态，强制落盘。
- `COMPLETED`：数据和元数据均已原子发布后才对客户端可见。
- 无法确认最终完整性时标记为 `INCOMPLETE` 或失败，允许导出已恢复数据，但不能显示为完整谱图。

任务完成不能只依据 TCP 暂时无数据。优先使用 LabVIEW/MSScan 的明确完成 PV；如果没有完成信号，应结合停止命令、连接状态、连续静默时间、终帧序号和预期点数判断。

#### 6.3.7 数据质量与可观测性

扫谱界面至少应显示：

- 当前 `run_id` 和数据来源；
- TCP/中继/LabVIEW/MSScan 各自状态；
- 最后数据距今时间；
- 最新 `frame_seq`、收到帧数和唯一点数；
- 重复帧、乱序帧、解析失败、校验失败和断线次数；
- 预计点数与当前完整度；
- 当前数据是否完整、恢复中或仅为部分数据。

服务日志应使用限频或聚合统计，不能像旧中继一样每转发 65536 字节就同步写一条日志，否则长扫描会产生大量磁盘 I/O。

还应记录命令参数与实际数据的一致性：磁铁实际电流是否落在扫描范围、点数是否符合步长、单位和质量标定版本是否明确、目标探测器是否与本次任务配置一致。

#### 6.3.8 网络与运行安全

- 监听地址优先绑定实验网专用网卡，不默认暴露到 `0.0.0.0`。
- 使用 Windows 防火墙限制来源 IP，只允许指定中继或 LabVIEW 主机。
- 一个端口只运行一个采集实例，启动时应检测占用并报错，不应强制杀掉未知占用进程。
- 配置连接超时、空闲超时、最大帧大小、最大扫描点数和磁盘剩余空间阈值。
- 采集进程崩溃重启后，应从持久化任务恢复接收状态或将旧任务明确标记为中断，不能悄悄清空旧批次。

#### 6.3.9 必须通过的验收测试

1. 将同一帧分别按每 1 字节、随机长度和 65536 字节边界分包，解析结果必须一致。
2. 一次 `recv` 包含多帧、帧头与帧体分别被拆开时不能丢帧或粘帧。
3. 连接在对象、数字和 UTF-8 字符中间断开，重连后不能拼出伪数据。
4. 重放相同全量帧不会增加唯一点数；更高版本全量帧能补齐先前缺点。
5. 缺失、重复、乱序 `frame_seq` 必须被识别并记录。
6. 相同起点、更高起点、反向扫描和重复 X 坐标不能混入上一批数据。
7. 扫描结束前最后一个短突发必须在完成前强制落盘。
8. 模拟 JSON 写入中断或原子替换失败，GUI 仍读取上一有效快照，不会读到半写文件。
9. 同时启动两个旧写入器或两个 TCP 来源时，系统必须拒绝冲突，不能混写。
10. 中继断开再恢复时，界面明确显示数据缺口；若有全量终帧，应完成补齐并通过点数与校验验证。
11. 接近最大点数和最大帧大小的长扫描不会阻塞 UI、无限增大内存或静默丢数据。
12. 服务或客户端在扫描中退出，已确认点仍可恢复，任务状态明确为中断或待恢复。

### 6.4 导出功能不完整

扫谱页目前显示“JSON 全参数”，但实际 JSON 仅包含扫描参数、质量换算系数、回落设置和点列。

相比原 demo，缺少：

- Ar/He 设定与回读；
- 腔体气压；
- 溅射功率、功率回读和打弧状态；
- JM、DW、BD 设备状态快照；
- 目标束流；
- condense length；
- LabVIEW 数据源、最新值和点数；
- 数据采集开始和结束时间。

当前默认文件名只是 `元素+三位序号+Ar-He`，没有写入实际 Ar、He、气压、功率和长度，和界面提示的 `元素-序号-Ar-He-气压Pa-PowerW-cm` 不一致。

TXT 按钮写着“仅电流”，但当界面选择 Mass X 轴时，当前实现会导出换算后的质量值。正确行为应是始终保留原始磁铁电流和束流强度，可选增加质量列，不能因显示模式改变原始数据导出语义。

### 6.5 成组扫描稳定判断不完整

当前成组扫描的 `readback_signal` 只指向第一台磁铁。服务端等待稳定时只检查这一路；`coordinate_spread` 又读取各路设定信号，而不是各路 `CurrentMonitor`。**（本轮已修，见 §8.3 第 2 行）**

**（本轮取证补充两条，改代码时别改错地方）**：
- 逐点写流程**已经**把四路设定都写下去了（`scan_service.py` 的写循环），"只写第一台"**只发生在回落路径**（见 6.6）——不要顺手去改扫描的写循环；
- 还有一个更隐蔽的洞：等待用 `setpoint_signals[0]` 取稳定容差（`scan_service.py:369`），而参数校验用的是 `any(...)`（`:237-240`）。只校验"某一路有判据"+只读第一路，会导致**四台磁铁全都没动、所有点仍然记为 `ok`**（实测复现）。

因此，目前无法识别“第一台到位、其余磁铁未到位”的情况。应把扫描轴契约改为多路回读，并要求：

1. 每一路都进入自己的稳定容差；
2. 记录每一路实际回读；
3. 用实际回读计算组内最大偏差；
4. 任一路掉线或超时，按配置选择记录异常点或终止任务。

### 6.6 回落功能存在错误实现

当前界面提供回落电流、回落速率、手动回落和完成后自动回落，但实际行为是：

- 成组轴只写第一个磁铁的电流设定；
- 回落速率只用于提示文字，没有写入 `CurrentRateSet`；
- 自动回落由客户端在看到任务终态后触发，客户端退出或崩溃时不会执行；
- 页面没有等待读回到位就显示“已回落”。

回落属于设备安全收尾，应移到扫描服务端状态机：先写全部目标磁铁的速率，再批量写回落电流，等待全部回读到位，最后才进入完成状态。失败时应保留设备锁并进入恢复待确认状态。

### 6.7 扫描终态持久化竞态

当前 `_finish_completed()` 先把内存状态切为 `completed`，随后才更新 SQLite。客户端或测试在这个窗口读状态时，可能看到内存已经完成、数据库仍是 `completing`。

**（本轮取证修正：受害方不是客户端。）** `status()` 只读内存，HTTP 也只暴露内存状态，所以客户端**看不到** `completing`；能撞上这个窗口的是测试与任何直读 SQLite 的进程（现场后果是"按库里终态驱动上传/清理"的组件把已完成的谱当成未完成）。窗口本身确实存在：`scan_service.py` 里内存置终态在库写之前，且库写在锁外。该问题本轮已按"先入库、后发布"修复。

2026-09-14 的定向测试实际出现一次：

```text
Ran 227 tests
FAILED (failures=1)

test_points_are_persisted_in_store:
数据库 state 为 completing，预期 completed
```

应调整状态发布顺序或增加事务边界，保证可见的终态和数据库终态一致。

### 6.8 扫谱暂停

当前暂停按钮有意禁用。原 demo 也没有完整、安全的任务暂停/恢复状态机。是否允许磁场长时间停在当前电流，需要现场确认，因此它不是本轮 demo 对齐的必补项。

## 7. 跨模块配置问题

### 7.1 PV 映射保存会丢失安全元数据

`PvMappingEntry` 已定义 `group`、`role`、`readback_signal`、`min_value / max_value`、`max_step / max_rate` 和 `settle_tol / settle_timeout`。

但设置页加载表格时不显示这些字段，保存时也不把原值合并回去。Pydantic 会接受缺失字段并填成默认空值，而不是阻止保存，所以这是实际的数据破坏风险。

建议将设置页拆成两层：

1. 普通映射表：标签、业务信号、PV、单位、可写、必需。
2. 高级设备参数抽屉：分组、角色、回读配对、边界、最大单步、最大速率和稳定判据。

即使暂时不开放高级字段编辑，保存普通字段时也必须按 `signal` 合并并保留未展示字段。

### 7.2 默认映射与模拟 IOC 范围不同

模拟 IOC 包含部分“台账补充”PV，例如 BD Reset/Error、JM01/JM07 设定与输出、MSScan/Scanz。它们没有进入默认应用映射，因此“模拟 IOC 可以 caget/caput”不代表页面或执行服务可以使用这些信号。

应把信号分为：

- 平台正式支持并进入受控映射；
- 仅用于联调或尚未确认含义；
- 已废弃或禁止使用。

不要继续用“SIM_ONLY”同时表达“实机存在但平台未接入”和“纯模拟信号”两种含义。

### 8.5 P0 之外顺带修掉的

- `POST /control/v1/signals/read` 请求不存在的信号名以前是未捕获异常 → **HTTP 500**（只看到"HTTP 500"，不知道哪个名字错）；现在返回 400 + 信号名。导出/快照一次读几十路时最容易踩到。
- **执行层的冷启动回读失败（真机实测踩到）**：`SignalWriteService.readback()` 与 `wait_settled()` **绕过 `_ensure_connected()` 直读网关**，而真实 CA 网关冷启动第一次访问要先建连——于是服务刚起来时"第一路回读必然失败"。调束取启动前快照因此被误判成"读不到"并拒绝启动（紧接着手工读同一路却是好的）。现在回读统一走一条**带建连保证**的路径（`_read_signal`），快照读取另加 3 次退避重试；补了两条"冷启动网关"回归用例。这条对所有路径都有效（扫谱等稳定、成组回落同样受益）。
- 导出时指定信号读失败会**自动回退为全量读**一次：现场很可能在设置页裁过映射，为缺一路就让整份工况快照变空不划算；回退成功时把原因写进 `unavailable.note`，回退也失败才按空快照导出（点列照常落盘）。
- `rate_signal` 纳入映射校验：配了但指向不存在/不可写的信号会在保存时被判出来，而不是等到成组回落时静默不下发速率。
- `ScanPoint.readback_values` 逐路回读落库（`scan_points.readbacks_json`），老库用**幂等 `ALTER TABLE`** 补列，不删库重建。

**P1.4 的两处工程取舍（如实记录）**：

- **阶段 1 不写"保持不动"的变量**：只读回它们的实际值并记进每一轮记录。对同一台设备反复写同一个值没有意义，还会白白增加设备动作与等待时间；而"当时它们在哪"事后必须查得到，所以读一定要读。
- **阶段 2 围绕每个变量自己的最优点收窄，而不是"最后一轮停在哪"**：逐参数阶段结束时设备停在最后一个候选上，那往往不是最好的点。报告说的是"各最优点 ± 原范围 × joint_frac/2"，所以每个变量单独记自己的最优（值 + 当时的目标），联合阶段据此居中。

**P1.3 的两处工程取舍（如实记录）**：

- **"应用最优"下发的是最优轮的「实际回读」，不是「候选值」**：候选值只代表算法想要的位置，设备实际到过哪里才是可复现的那一组参数（若那一轮回读未稳定，`quality` 也一并记着）。
- **动作重新申请设备组，而不是复用任务结束时的旧锁**：任务结束时锁已经交还（否则别的任务永远起不来），所以处置动作必须像新任务一样去抢组——抢不到就 409 并点名占用者，绝不绕过锁偷偷写。

**P1.2 的三处工程取舍（如实记录）**：

- **拿不到快照就拒绝启动**：任何一路参与变量的实际回读读不到时直接 `failed`，并在消息里点名是哪一路。理由很直接——没有快照就无法在束流异常时把它退回去，"先跑起来再说"在这种场合是拿设备赌。
- **目标基线读不到不拒绝**：只是相对损失判据不可用，会写进 `snapshot_note` 并在界面显示；此时保护退化为"只看绝对阈值"。**不拿猜测的数字当安全边界**。
- **成功的回退用 `aborted` 收尾，没有新造状态**：报告只规定了"回退失败 → `RECOVERY_REQUIRED`"，成功路径的状态没规定。这里沿用 `aborted`，但把原因写进状态消息 + `recovery` 结构，界面上独立一条"⚠ 束流丢失保护…"逐路列出实际回读。若要单独一个 `safe_recovered` 状态，需要动状态表与客户端文案，留作后续。
- **顺带修掉「初始回读」含义错误**：结果页的"参数变化"起点改为**启动前快照**（没有快照时才退回第一轮回读，并在表下注明），"相对提升"也改用目标基线而不是第一轮目标值。

**P1.1 的三处工程取舍（如实记录）**：

- **磁铁速率永远不进变量列表**：即使有人在映射文件里把它手改成 `tunable=true`，目录层也会拦下（`NEVER_TUNABLE_SUFFIXES`）——把变化速率当搜索维度会让设备运动变得不可预测。
- **联动组（磁铁 1+2 / 3+4 / 1~4）本轮只作信息呈现**：成组调束要求服务端**原子批量下发**，否则一轮里分 4 次写会留下"部分成功"的中间状态。界面提示里写明了这一点，没有做成"选了就自动成组"的假功能。
- **束线顺序是可配置的工程假设**：顺序取自台账/界面既有的组顺序，探测器归属按束流探测组。现场核对实际布置后只改 `packages/domain/beamline.py` 即可，界面与执行层不用动。

### 8.7 环境坑（这轮踩到，记下来免得重复）

- **「等待确认」的调束任务会一直占着设备组**（设备处于半优化状态，这是设计如此）。自检或客户端中途退出就会把锁留在执行服务里，后续扫谱/调束全部收到「设备组不可用」。现在 `tools/check_tuning_page_live.py` 会自己收尾（停止 + 必要时人工确认），实测：`awaiting_confirmation` 占用 `['束流探测','磁铁电源']` → 收尾后 `aborted` / `[]`，紧接着的扫谱正常完成。
- **跑 UI 相关测试必须设 `QT_QPA_FONTDIR=C:\Windows\Fonts`**：不设时 Qt 没有字体、文本度量变化，设置页最小宽度会越过 900px 的紧凑断点，`test_settings_navigation_switches_responsively` 会误报失败。

**P2.1 的两处设计取舍（如实记录）**：

- **校验用执行层的干跑（`dry_run=True`）而不是另写一套规则**：批量预校验必须与正式写入**完全同一套**边界/单步/速率逻辑，否则会出现"预检说行、真写被拒"。干跑顺带做了"当前值可读"检查——读不到当前值就不该下这批（无法判断变化量）。
- **抢不到设备组时返回 200 + `ok=false` 而不是 409**：成组接口的响应契约明确区分"整批未写 / 部分成功 / 全成功"三种结局，调用方只需处理一种响应形状；`nothing_written=true` 就是"一次都没写"的明确信号。而单点/回落端点保持 409（那是并发冲突的异常语义）。**接口之间这点差异是有意的，已在契约注释里写明。**

**P2.2 的三处设计取舍（如实记录）**：

- **开关是环境变量而不是配置文件/接口**：它表达的是"这台机器被部署成只读"，属于启动方式的一部分，改动它必然伴随一次重启——比放在一个能被 API 覆盖的配置字段里可靠得多（那个字段一旦被改，只读就名存实亡）。默认关闭：不写这个变量就等于可写，现场升级不需要额外动作。
- **"启动即 400"与"200 + 理由"两种口径并存，是按动作性质分的**：扫谱/调束/保存映射是**没法进行下去**的动作，启动阶段说清最省事（也不会留下半截任务与半开状态）；单点/成组/回落则沿用既有"一律 200 + 逐路理由"的契约——写被拒是**设备没动**这个正常结局，改成异常会让调用方在两个分支里各写一套。
- **界面锁只是"不撒谎"，不是防线**：四个页面都压住了按钮并写了原因，但每一处另有一道同语义的程序化拦截（`start_scan` / `_manual_retract` / `start_tuning` / `_approve` / `finalize_tuning` / `_save_pv_mapping` 都先自查再发请求）。真正的强制点只有执行层一个——这样即便某个客户端版本旧、或者有人绕过界面直接调 HTTP，结论也一样。

**P2.3 的两处设计取舍（如实记录）**：

- **不跟随 demo 的"改一次范围就自动存盘"（0.5 s 节流）**：那是击键级写盘，而且会把**输到一半的范围**存成"上次配置"（输入 1 想打 150，存下来就是 1）。改成三件事：显式「保存调束配置」、**开跑前自动存一次**、打开页面自动载回一次。既保住了"下次打开还是这一套"，又不会把没填完的状态当配置。
- **配置里不夹范围、也不拿它当写权限**：保存的范围原样保留、载入时按控件范围夹（越界时第一道提示），真正能不能写、写多少仍由执行层在启动时按**当前映射**校验。所以配置文件是"操作便利"，不是"设备档案"——换设备/换映射时它只会点名缺失信号，不会绕过任何安全校验。

**P2.4 的三处设计取舍（如实记录）**：

- **分析全部在客户端算，服务端只补了一条"事实"**：响应曲线、建议、日志都只依赖已落盘的轮次记录，所以客户端算（规则随现场经验改，改一次就能用；也不再给服务端加一套"结论接口"）。唯一往服务端加的是**每轮所属阶段**——那个信息只存在于运行内存里，不落盘就等于永久丢失，而事后复盘分不清"哪几轮是逐参数、哪几轮是联合"时，日志和曲线都会读错。
- **不照搬原 demo 的"初始采样数"**：平台的第一个候选固定取范围中心（`packages/optimizer/bayes.py`：比随机点更容易被现场接受、也便于复现），根本没有"随机初始撒点"这件事。给一个**不受任何代码影响**的输入框只会让人以为改了它就换了行为——要更随机地探索，用观测噪声与随机种子。这一项如实记成"平台不做"，而不是补一个假开关。
- **建议只提示、只触发一次，也不写"最优在范围外"这种结论**：贴边不等于最优在范围外，停滞也不等于到了物理上限。文案写成「看到什么 + 建议查什么」，把判断留给操作员；每条规则只出现一次，免得每轮刷屏把真正的新信息淹掉。

**另外修掉两处在线自检的"瞬时采样"误报**（`tools/check_manual_page_live.py`，连续跑 5 次才稳定复现）：

| 误报 | 原因（实测取证） | 修法 |
|---|---|---|
| 「新一次下发清掉上一次的标红」偶发失败 | 断言只接受 `state ∈ {"", "warn"}`——但回读一旦进容差，这一行会显示 `good`（≈ 已稳定）。写 320 之后那一帧正好读到 320 时就是 `good`。**产品行为是对的**：临时脚本连跑 8 轮，每轮 `rejected_flag=False`，终态是 `""` 或 `good`，从没停在 `error` | 断言改成"**不是 error**"（三种状态都代表标红已清掉），并等到状态稳定再断言 |
| 「按钮选中态跟随实际回读」偶发失败 | 按钮选中态按**回读值**每个轮询周期刷一次，点完立刻断言会撞上"回读还没回来"那一帧 | 改成等待其跟随到位（或服务端明确拒绝），有界 10 s |

顺手把这两处依赖的"消息区文案"改成先清空再提交：不清空时 `pump` 可能被**上一次**留下的"已下发/被拒绝"立刻满足，断言实际看的是旧结果。
