## 1. 原方案条目落地核对

v1 的条目多数已在本仓库落地。核对结论（依据当前代码）：

| v1 条目 | 状态 | 依据 / 缺口 |
|---|---|---|
| 4.1.1 Optuna / cmaes / dashboard 依赖进正式依赖 | **已落地** | `pyproject.toml` 的 `service` extra 含 `optuna`、`cmaes`、`optuna-dashboard`、`scikit-learn` |
| 4.1.1 引擎能力接口 | **已落地** | `GET /control/v1/tuning/capabilities`；客户端 `_on_capabilities` 用它决定 Dashboard 入口 |
| 4.1.2 自动模式必须有有效束流保护 | **部分落地** | 服务端 `_validate` + 基线读不到时二次拒绝；但状态里没有 `protection_ready` / `protection_reasons`，界面无法展示"保护是否真的有效" |
| 4.1.3 整组候选 dry-run 预检 | **未落地** | 执行层 `SignalWriteRequest.dry_run` 已具备，但调束仍逐路写：前一路已动、后一路被拒即形成部分执行 |
| 4.1.4 质量状态与优化器接纳规则 | **部分落地** | `ok/unsettled/read_failed/write_rejected` 已区分并保存；但 `unsettled` 仍会喂给优化器并计入历史最优（见 7.1 表） |
| 4.1.5 Trial 生命周期 | **已落地** | `OptunaAsker.fail_trial` / `drop_pending_trial`；非 ok 轮次不 observe |
| 4.1.6 `safe_value` 语义统一 | **未落地** | "回安全值"仍取 `entry.min_value`，缺失时静默用 `0`（`_finalize_targets`），映射里的 `safe_value` 未被使用 |
| 4.2.1 增量拉取 + progress 接口 | **部分落地** | 客户端已有 `_last_completed` 计数门与 `_iterations_in_flight`；无 `revision` / `progress` 原子接口，计数不一致时会退化成每 700ms 全量重拉 |
| 4.2.2 暂停/停止请求语义 | **部分落地** | 停止已是"本轮收尾后停"；暂停只在 `RUNNING`/`AWAITING_CONFIRMATION` 可提交，auto 模式窗口很短，界面按钮长期不可点 |
| 4.2.3 断线与错误可见反馈 | **未落地** | 轮询失败被静默忽略（`_on_status` 直接 return），界面不显示"与执行服务失去连接" |
| 4.3.1 采样 Study / 分析 Study 分离 | **部分落地** | 采样 Study 已按阶段拆分（`run_{id}__sample__{stage}[_{signal}]`）；**没有独立分析 Study**，`open_study` 直接合并采样 Study → 重要性与响应面混了逐参数阶段与联合阶段数据 |
| 4.3.1 分析参数用实际回读 | **未落地** | 分析取 Optuna `trial.params`（suggested 值），不是设备实际回读 |
| 4.3.2 暂存库与分析库对账 | **未落地** | 无 `run_id + iteration` 对账，无数据版本 / 最后同步时间展示 |
| 4.3.3 分析能力（history/importance/slice/contour/parallel） | **部分落地** | history / importance / slice / surface 已有；**缺二维 contour 与平行坐标**；重要性可信门槛仍是 `n_complete >= 3` |
| 4.3.4 共用画布被清空 | **已落地** | 结果分析用独立 `SpectrumPlot`，`_clear_result_analysis_items` 只清自己加的图元 |
| 5.1 引擎分层 | **已落地** | UI 默认 `cmaes`（实测对比后改默认），保留 tpe/qmc/random/grid |
| 5.3 预测字段语义 | **部分落地** | `predicted/std` 已在候选文案展示，但 TPE 等采样器也会显示"预测 ± 不确定度"，语义上仍是伪装的模型预测 |
| 6.x 8081 Dashboard 组合形态 | **已落地** | capabilities 返回 dashboard 可用性与 URL，结果页有入口按钮 |
| 7.x 三阶段 UI/UX 重构 | **部分落地** | 三段页签已存在、预检与运行计划已有；但布局密度、图表质量、日志详细度仍不达标（本轮重点） |
| 8.1 / 8.2 契约扩展（phase / revision / duration / spread） | **未落地** | `TuningIteration` 仍只有轮末一个 `at`；无 `phase`、无耗时、无采样离散度 |
| 8.3 历史任务访问 | **部分落地** | `/tuning/runs` 列表与 `/analysis` 已在服务端；客户端没有历史任务入口，也不认领正在运行的任务 |

**结论**：v1 的"正确性与安全"主体已闭合；本轮把重点放在用户实际感知的四个方面——
**界面密度、图表质量、过程可追溯（时间戳日志）、以及仍存在的逻辑缺陷**。

## 2. 改进原则（沿用 v1，继续有效）

1. **安全优先于优化效率**：采样器只能提候选；白名单、束线上下游、设备硬边界、最大单步/速率、
   设备组互斥、应用层联锁、束流保护、启动前快照与回退，全部由服务端强制执行；界面预检不得替代。
2. **设备事实与算法建议分开**：`proposed / applied / readback / objective / quality` 五者分别记录与展示；
   运行监控与设备处置以**实际回读**为准。
3. **单一事实来源**：`tuning_spool.sqlite3` 的 run/iteration 是审计事实；Optuna Study 是采样与分析投影，
   二者必须能按 `run_id + iteration` 对账。
4. **渐进实施**：先稳妥修正确性，再做界面与图表，最后补日志与对账；每批独立验收。

## 5. 方案 B：图表科研风 + 流式渲染

### 5.1 统一绘图样式（新增 `apps/desktop_client/plot_style.py`）

- 坐标轴：上/右保留边框刻度、刻度线向内、次刻度、10pt 刻度字号、轴标签带单位；
- 网格：主轴 `alpha≈0.12`，零线/基线加粗一档；
- 图例：无边框、半透明底、置于不遮挡数据处，可关闭；
- 颜色：全部取主题 token；响应面用 `viridis`（均值）与 `plasma`/`inferno`（不确定性），并**成对给出 colorbar**；
- 标注：最优/最差点、阈值线、阶段分界、面板标号 (a)(b)；
- 导出：PNG（300dpi）/ PDF / SVG（矢量）+ 图上标注数据来源（study 名、算法、种子、有效轮次）。

### 5.2 流式渲染（`spectrum_plot.py`）

- 新增 `append_point()` / `update_stream()`：增量追加，不再每次 `set_data` 全量替换；
- 10Hz 合并重绘（取数 700ms 节奏与渲染节奏解耦）；
- **轴稳定策略**：y 轴"只扩不缩 + 5% 迟滞"，x 轴"跟随最新 N 轮 / 全范围"可切换，保留"复位视图"；
- 增量更新时不重建散点与标签对象（消除每轮闪烁）；
- 基准线/阈值线独立图元，避免与业务曲线互相清除。

### 5.3 各分析图重做

| 视图 | 现状 | 目标 |
|---|---|---|
| 优化历史（爬山图） | 单条折线 + 最优虚线 | 实测散点（**多次采样误差棒**）+ best-so-far 阶梯线 + 基线/目标虚线 + 最优点标注 + 停滞区间淡底 |
| 参数重要性 | 固定浅蓝柱 | 水平条形、按值排序、数值标注；trial 不足时明示"数据不足，不给出稳定排名"（门槛 `n_complete ≥ max(10, 3×参数数)`） |
| 单参数切片 | 裸散点 | 散点 + GP 均值曲线 + 不确定性带 + rug 采样密度 + 最优点竖线 |
| 双参数轮廓 | 无 | **新增**：等高线 + 采样点着色投影 + 最优点十字 |
| 响应面矩阵 | 220×170 固定格、逐格独立色标、无 colorbar | 格子按视口自适应 `clamp(140,(W-gap·(n-1))/n,220)`、成对 colorbar、等高线叠加、采样点投影、最优十字、**点格放大**、导出 |
| Trial 明细 | 基础表 | 质量状态着色、可按列排序、有效/未稳定/失败筛选 |

## 6. 方案 C：带时间戳的详细过程日志

### 6.1 契约扩展（`packages/contracts/tuning.py`）

`TuningIteration` 增加（全部可选，旧记录为 None，向后兼容）：
`proposed_at`、`applied_at`、`settled_at`、`measured_at`、`duration_ms`、`sample_count`、
`sample_median`、`sample_spread`（MAD/IQR）、`samples`（可选长期保存）、`failure_step`。

`TuningRunStatus` 增加：`revision`（单调递增）、`phase`
（`proposing/prechecking/writing/settling/holding/measuring/recording/waiting_confirmation/idle_between_iterations`）、
`latest_objective`、`best_iteration`、`pause_requested`、`stop_requested`、`protection_ready`、`protection_reasons`。

### 6.2 服务端事件日志（新增）

- 存储：`tuning_events(run_id, seq, at, level, phase, iteration, message, data_json)`，
  迁移走 `tuning_store.MIGRATIONS`（幂等，不删库）；`seq` 每 run 单调递增。
- 覆盖事件：建任务 / 校验（含拒绝原因）/ 占设备组 / 复位 / 快照（逐路）/ 目标基线 / 提候选 /
  逐路写入（含执行层拒绝原因）/ 等稳定结果与耗时 / 逐次采样读数 / 目标计算 / 质量判定 /
  最优刷新 / 异常计数 / 保护触发 / 逐路回退 / 暂停 · 继续 · 停止请求 / 早停 / 完成 /
  处置（逐路）/ 错误与断线。
- 接口：
  - `GET /control/v1/tuning/runs/{run_id}/events?since=<seq>`（增量事件）；
  - `GET /control/v1/tuning/runs/{run_id}/progress?after_iteration=<n>`（v1 §4.2.1 的原子进度：
    状态 + 新增轮次一次返回，消除 status / iterations 乱序）。
- 保留策略：默认保留最近 N 个 run 的完整事件（可配置），更早的只保留轮次记录。

### 6.3 客户端
