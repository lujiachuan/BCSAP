# 评审意见：《PV 读写延迟与稳定性改进报告》

> 评审日期：2026-09-24  
> 评审对象：`docs/PV读写延迟与稳定性改进报告.md`（652 行，评审稿）  
> 评审目的：确认报告是否能支撑"保证 PV 连接稳定、提升读写速率"这一目标  
> 复核方式：逐条对照源码 + 在本地模拟 IOC 上实测网关延迟与命令数（见 §7）

## 1. 总体结论

报告的方向判断是对的，安全论证也基本成立：**不要为了延迟去动超时、不要并行 caput、不要直接启用现有长连接网关、不要在设备确认前放宽 `max_step/max_rate`**——这几条结论经代码复核全部成立，建议保留。

但有三个层面的问题影响它作为决策依据的可信度：

1. **有一处硬错误、一处不可复核、两处自相矛盾**（§2）；
2. **漏掉了若干真实风险，其中一条是安全级的**（§3）；
3. **把瓶颈定位偏了**：实测健康路径已经是 1 个进程 / p95 137 ms，报告的"正常读取效率中等"和"长连接阶段才能到 0.3 s"的假设不成立；真正的、也是唯一的长尾来源是**二分补探**（§5、§6）。

一句话建议：**报告的阶段划分可以保留，但优先级要改**——把"补探收敛 + `-w` 显式化 + 写入总时限 + 接口层禁止"未连接却给值""提到阶段 0/1，阶段 3（持久 CA 子进程）从"降低正常延迟的必要手段"降级为"仅当耐久测试暴露进程/建连问题时才做"。

## 2. 必须修正的事实性问题

### 2.1 §2.2 "61 项通过"不可复核（证据链缺口）

`tests/test_signal_batch.py` 在我这个受限沙箱里 12 项全失败，原因是 `tempfile.TemporaryDirectory()` 目录不可写导致
`sqlite3.OperationalError: unable to open database file`（环境问题，不是代码缺陷）：

```text
test_command_line_epics.py   10 passed
test_signal_io.py            39 passed
test_signal_batch.py         12 failed（沙箱临时目录写权限）
```

10 + 39 + 12 = 61，与报告的"61 项通过"吻合，说明**原始结论大概是真的**，但报告必须补上：完整命令、Python/pytest 版本、是否使用 `.venv`。否则任何人换台机器复核都可能得到与我一样的"12 failed"，直接动摇整份报告的证据基础。

### 2.2 §6.2 SLO 与代码常量矛盾

| SLO 行 | 问题 |
|---|---|
| "可见关键 PV 离线恢复发现 ≤ 3 秒" | `CommandLineEpicsGateway.OFFLINE_RETRY_S = 10.0`（`command_line.py:27`）。隔离期内根本不会重探，**最快发现时间就是 ~10 s + 探针耗时**，与 ≤3 s 直接冲突。报告只写了"非关键隐藏 PV 可维持 10 秒退避"，没有说明可见 PV 的退避改成多少、由谁配置。 |
| "单步写入服务端排队 p95 ≤ 1.0 秒" | 当前服务端**没有排队路径**：`DeviceLockManager.acquire()` 冲突即抛 `DeviceBusy`（`device_locks.py:44-53`），`runtime.write_signal()` 立刻返回拒绝（`runtime.py:120-133`），客户端 `request_write()` 忙时直接返回 `None`（`instrument_api.py:547-550`）。这一行应改成"锁冲突拒绝率"，把"排队 p95"留给阶段 2 的调度器。 |

### 2.3 §4.2 "三个外部命令的理论超时累计可接近 9 秒"误导读者

`caget -h` 明确写着 `-w <sec>: Wait time, specifies CA timeout, default is 1.000000 second(s)`；代码里**从不传 `-w`**（`command_line.py:167-171`），所以离线 PV 的实际单命令耗时是 **~1.07 s**，不是 3 s：

```text
caget -n <不存在的 PV>           1073 ms  exit=1（默认 -w 1.0）
caget -w 0.2 -n <不存在的 PV>     266 ms  exit=1
```

3.0 s 只是 Python 侧的兜底（防止进程真卡死），**不是运行点**。写"3 个命令最多 9 秒"会让读者以为离线场景的代价是 9 s；真实代价是 ~3.2 s，而真正的长尾来自二分补探（§3.4、§5）。同时报告完全没提 `-w` 这个可以直接调、且直接决定长尾的关键参数。

### 2.4 §4.1 对"20 秒长尾"的出现频率描述不准

实测（§5）1 路离线在 128 路映射里的形态是：

- **首次发现**：15 个进程、9.5–9.7 s（不是 20 s，也不是"每次都快照 20 s"）；
- **随后 10 s 内**：1 个命令、~100 ms（被离线隔离挡掉）；
- **退避到期**：1 次单路重探，默认 `-w` 下 ~1.1 s。

所以稳态是"一次 ~9.5 s 卡顿，之后每 10 s 一次 ~1.1 s 小卡"，而不是"每次慢读都 20 s"。报告方向没错，但量级与频次要写准，否则阶段 1 的收益会被高估。

### 2.5 §5.2 R4/R5 的幂等范围被放大

幂等只覆盖**客户端自带 `command_id`** 的写入：手动单点（`instrument_api.py:183`）与成组写入。扫谱、调束、回落这三条路径构造 `SignalWriteRequest` 时**都不带 `command_id`**（`scan_service.py:406`、`tuning_service.py:1544`、`retract.py:74,84`），它们的"不重复写"完全依赖服务端状态机与回读判据。报告应明确写出这个范围，否则读者会以为全链路都有幂等保护。

## 3. 报告遗漏的风险（按优先级）

### N1（P0，安全）：`connected=False` 的读数会被当成真值 0.0

`SignalWriteService._signal_reading()` 无论是否连接都写 `value=float(reading.value)`（`signal_io.py:162`），而 `read_value()` / `_read_signal()` 直接取 `.value`（`signal_io.py:172-185`）。今天不出问题，只是因为 `CommandLineEpicsGateway.read()` 对离线 PV **抛异常**（`command_line.py:62-66` 未传 `allow_nonzero`），走到 `except` 分支返回 `value=None`。

一旦按报告 §7.4 换成会返回 `connected=False` 的网关（现有 `ChannelAccessGateway.read()` 正是这种行为，`channel_access.py:364-375`），后果是：

- `wait_settled()` 的 `current()` 得到 0.0 → 若目标值为 0（**回落目标就是 0 A**）且容差 ≥ 0，直接判定"已稳定"（`signal_io.py:414-417`）→ 回落会报告成功但设备从未被确认；
- 扫谱探测器采样 `read_value()` 得到 0.0 → `samples` 非空 → 该点以 `quality="ok"` 进谱图（`scan_service.py:448-484`），而代码在别处专门防着"把 0 当成真实强度"。

这正好命中报告 §9.3 的红线"回读未稳定却被记录为有效扫描点"。**报告 §7.4 的读取切换步骤必须补一条前置改造：接口层禁止"未连接却返回值"，`SignalReading.value` 在未连接时必须为 `None`，并在阶段 3 的影子里对这一条做断言。**

### N2（P0）：写入没有服务端总时限，最坏情况是"客户端早已放弃、服务端还在写"

`_execute()` 的斜坡循环每步都过一遍 `gateway.write()`（`signal_io.py:305-309`），而 `gateway.write()` **每一步都要抢 `_snapshot_lock` 并各自带 3 s 超时**（`command_line.py:74-79`）。因此单次写入的服务端最坏耗时 ≈ `N步 × (20 s 快照等待 + 3 s 命令)`：

- 128 步上限（`MAX_RAMP_STEPS`，`signal_io.py:34`）→ 最坏 ~49 分钟；
- 客户端写超时只有 120 s（`instrument_api.py:42`），成组 60 s、回落 120 s、调束确认 180 s；
- 期间 `write_signal()` 一直持有设备组锁（`runtime.py:121-137`），同组的新请求全部被 `DeviceBusy` 拒绝，而操作员**没有任何接口能查到"那次超时的写还在不在跑"**。

报告 R6 描述了这个现象，但没有给出这个复合上界，也没提"锁被长期占用 + 无法查询"这两个后果。建议：给写入操作加服务端硬截止时间（预读→斜坡→回读整体），并暴露操作状态查询接口；客户端超时应从服务端上界反推，而不是各自拍。

### N3（P0）：没有全局子进程上限；进程创建失败被伪装成"设备状态未知"

三条独立的起进程路径没有任何全局约束：快照补探（≤32 个/次，`command_line.py:25`）、单路 `read()`（无限制）、斜坡每步 `caput`。而 `_run()` 把任何 `OSError`（含"无法创建进程"）统一转成 `ConnectionError`（`command_line.py:234-235`），写入路径再把它标成 `device_state_unknown=True`（`signal_io.py:310-315`）——**机器资源紧张会被报成"设备状态未知，请人工确认"**，既丢可用性又误导排查。建议：全局信号量 + 把"进程未能启动"与"命令已下发但结果未知"分成两种状态。

### N4（P0）：单路 `read()` 没有离线退避、没有命令预算

`CommandLineEpicsGateway.read()` 完全不碰 `_offline_until`（对比 `snapshot()` 的 `command_line.py:98-104`）。于是控制路径上的离线 PV 每次都付满 1.07 s：

```text
离线单路 read() 连续 5 次：1064 / 1072 / 1090 / 1047 / 1078 ms（无退避、无缓存）
```

后果不是"慢一点"：`wait_settled()` 默认 0.2 s 轮询（`signal_io.py:414-420`），离线回读下每轮变 1.27 s，绕完磁铁 60 s 的 `settle_timeout`（`device_profiles.py:318`）要起 **~47 个进程**，最后仍判 `unsettled`；扫谱在 `on_unsettled="fail"` 下会**整场失败**（`scan_service.py:442-446`），而不是"界面卡一下"。报告把离线 PV 的影响只写在 UI 层面（R9），低估了它对任务成败的影响。

### N5（P1）：斜坡与页面快照的碰撞是"必然"而不是"偶发"

`write()` 每写一步都 `self._snapshot_cache.clear()`（`command_line.py:76-77`）——清的是**整张表**。所以斜坡进行中，手动页下一次 1 s 轮询必然缓存不命中，必然发起全量批量读，必然与下一步 `caput` 抢锁。再叠加调束页每 2 s 刷新回读（`pages/tuning.py:3121-3133`）和调束稳定轮询每 0.2 s 一次批量快照（`tuning_service.py:1785-1799`），报告 §3.2 只把"手动页 1 s 轮询"算作背景负载，明显偏低。建议：失效只清被写信号（及其回读），页面读在抢不到锁时返回"上一份快照 + 年龄"而不是阻塞。

### N6（P1）：成组写入的"原子校验"会真实读设备，且发生在拿锁之前

`runtime.write_batch()` 先对每一路做 `dry_run=True` 的写入（`runtime.py:324-338`），而 `dry_run` 在 `_execute()` 里**是在真实读设备之后**才返回的（`signal_io.py:275-299`）。实测确认：

```text
dry_run 校验 magnet.m4: 受理=True 耗时=93 ms 命令=1（caget 93ms）
```

所以 4 路成组写 = 4 次干跑读 + 4 路正式写（每路再各一次写前读）。报告 §4.2 的时序模型**完全没有覆盖成组路径**，而这条路径每路多花一个最多 3 s 的命令。另外干跑发生在拿设备组锁之前（锁在 `runtime.py:352-374`），"整批合格"的判定在锁外，语义比文档描述的"原子"要弱。建议：先取组锁，再把"干跑读 + 正式下发"合成一个事务，复用同一次写前读。

### N7（P1）：不可解析的 PV 与不可达的 PV 无法区分

`_parse_batch()` 对非数值行直接 `continue`（`command_line.py:246-257`），`_snapshot_locked()` 再把"没解析出值"一律当离线处理（`command_line.py:133-136`）。一个字符串/枚举/波形 PV（或映射里填错类型）会**永久显示离线**，并把整页每 10 s 拖慢 ~1.1 s，永远无法自愈，页面上也看不出原因。caget 的 stderr 其实区分了 `not found` 与 `Channel connect timed out`（测试夹具里就能看到，`tests/test_command_line_epics.py:75,100`），`_run()` 也已经把 stderr 收进 `detail`（`command_line.py:236-244`）——建议据此把"永久不存在/不可解析"与"暂时不可达"分成两种状态、两种退避。报告 §7.1 的基线清单只提到"错误地址"，没提这个更常见的坑。

### N8（P1）：多页共用一个快照锁，`T_queue` 在报告里是无界的

`snapshot()` 全程持 `_snapshot_lock`（`command_line.py:86-87`），而服务端是 FastAPI 同步端点（`app.py:153-167`），每个请求占用一个线程池线程。手动页 + 调束页 + 扫描页 + 设置页各用自己的"在飞抑制"，**服务端没有并发准入**。当 1 路离线造成 9.5 s 快照时，第二个页面的端到端延迟 = 自己的一次探针 + 前面排队的那次，轻松越过 30 s 客户端读超时（`instrument_api.py:40`）→ 操作员看到"读取失败"，而服务其实是健康的。报告的公式里有 `T_queue`，但正文和 SLO 都没给它上界。

### N9（P2）：保护性回落可能被自己的客户端超时打断

`retract_signals()` 逐路 `wait_settled()`，磁铁 `settle_timeout=60 s`（`retract.py:99-108`、`device_profiles.py:318`），4 路串行最坏 240 s，而客户端 `MAGNET_RETRACT_TIMEOUT_S=120`（`instrument_api.py:52`）。**一个安全动作会在界面上显示成"超时"**，而服务端仍在回落并占着组锁。建议：给回落单独的状态查询 + 界面明确的"回落进行中"语义，并把客户端超时改成服务端上界的函数。

### N10（P2）：阶段 3 的设计输入不足——现有 CA 网关的问题比报告列的更多

报告 §5.3 只指出"`_submit()` 超时不会取消 CA 线程里的任务"。复核后还应写入以下设计约束（否则"把 CA 放进子进程"会重复同样的坑）：

| 位置 | 问题 |
|---|---|
| `channel_access.py:238-248` | CA 线程空闲时阻塞在 `queue.get()`，**不调用 `ca_pend_event`**；而上下文是非抢占模式（`ca_context_create(0)`，`:227`）——空闲期间 CA 的后台搜索/beacon/保活根本不被处理，掉线通道不会自愈。 |
| `channel_access.py:213,309` | 任务队列无界：超时后调用方走了，队列继续堆积并逐个执行。 |
| `channel_access.py:454-459` | `close()` 只是把哨兵 `None` 追加到**队尾**再 `join(5.0)`——排不空就会留下仍在执行排队任务的线程，即"进程已关闭仍发生晚到写入"。 |
| `channel_access.py:325-351` | `_connected` 一旦置真永不复位；IOC/网络重启后 `connect()` 直接返回 True 不再探测。 |
| `channel_access.py:368,427` | 未连接时返回 `value=0.0`（配合 N1 会成为安全缺陷）。 |

另外 `FailoverEpicsGateway`（`command_line.py:306-363`）**在生产里没有任何调用点**（只有 `tests/` 引用），且它把首个成功的后端永久缓存在 `_active` 里——既不回切也不重探。报告 §7.4 说"命令行工具保留为人工诊断通道，不在状态未知写入中自动切换后端"，方向正确，但应顺带指出这个死代码的陷阱，避免有人"顺手启用"。`tools/check_signal_chain.py:48` 的注释"默认工厂 = 真实 ChannelAccessGateway"也已经与 `create_gateway()` 的现实（只用命令行网关，`pv_health.py:26-37`）不符。

## 4. 报告写得对、评审时不要改的部分

以下结论经代码复核成立，建议原样保留：

- 写入安全边界清单（只读模式、可写性、有限性、上下界、单步、速率、组锁、状态未知、人工确认）与拒绝顺序（`signal_io.py:230-315`）；
- "写前读必须用现场值、不得用 UI 缓存"（`_execute()` 确实走真实读，`:275-283`）；
- 状态未知不自动重放、只有回读确认在原位才有限重试（`tuning_service.py:1521-1618`）；
- R7"逐项 `latency_ms` 失真"完全正确——`check_pv_health()` 先整体 `snapshot()`，再做逐项计时（`pv_health.py:89-108`）；
- R8"命令行网关没有 IOC 时间戳"正确（`command_line.py:267-276` 令 `source_time == received_time`）；
- 不降低 3 s 超时、不并发 `caput`、不直接启用现有 CA 网关、不自动重试超时写入、不擅自放宽 `max_step/max_rate`；
- 阶段顺序（测量 → 收窄读取 → 幂等 → 优先级调度 → 持久 CA → 设备侧优化）与 §9.3 的安全红线。

## 5. 本次补充的实测基线（本地模拟 IOC）

环境：`sim/ioc.db`（154 条记录，覆盖全部 128 路映射）+ `EPICS_CA_ADDR_LIST=127.0.0.1`、`EPICS_CA_AUTO_ADDR_LIST=NO`（钉死本地，不会触及真实束线）。**这只能作为形态与量级的参考，现场必须在真实控制网上重测。**

| 场景 | 命令数 | 实测耗时 |
|---|---:|---|
| 全在线 128 路全量快照 ×40（1 s 节拍） | 1 | **p50 122 ms / p95 137 ms / max 143 ms**，无一次补探、无误判离线 |
| 128 路中 1 路离线：首次发现 | 15 | **9.5–9.7 s**（其中 8 个命令各等满 CA 超时） |
| 同上：隔离窗口内快照 | 1 | 76–160 ms |
| 同上：退避到期单路重探（默认 `-w 1.0`） | 2 | 1.21 s |
| 同上：`-w 0.3` / `-w 2.0`（同一次重探） | 2 | **0.51 s / 2.20 s** |
| 在线单路 `read()`（0.2 s 节拍） | 1 | p50 83 ms |
| 离线单路 `read()`（无退避无缓存） | 1 | 1.05–1.09 s（每次都一样） |
| 单步写入（1 步斜坡） | 3 | 344 ms（写前读 + caput + 写后回读） |
| 2 步斜坡（150 A 变化） | 4 | 1.92 s（步间等待 1.5 s，命令 ~0.4 s） |
| 6 步斜坡（600→50 A） | 8 | 10.18 s（步间等待 10 s，命令 ~1 s） |
| 成组写的 `dry_run` 校验（单路） | 1 | 93 ms（确认会真实读设备） |
| 单个 `caget`：在线 / 离线 | 1 | 81 ms / 1073 ms |

**由此得到两条与报告结论不同的判断：**

1. **健康路径不是瓶颈。** 1 个进程、p95 137 ms，已经优于报告第一阶段 SLO（≤1.0 s），也**已经达到报告给"长连接阶段"定的 ≤0.3 s 候选目标**。报告 §1 的"正常读取效率中等""长连接可显著降低正常延迟"高估了阶段 3 的收益：从 137 ms 降到理论 ~20 ms，换来的是"写任务无法取消 / 晚到写入 / 进程级重启"这一整类风险。建议把阶段 3 明确降级为**可选**，并用现场耐久数据（是否真的出现进程/建连问题）作为唯一触发条件。
2. **长尾唯一来源是二分补探**，而它由两个可调因子决定：探测范围（多少路进同一次批量）与 `-w`。报告阶段 1（只读页面实际用到的信号）能把 128 → 十几路，直接把 15 个命令的补探树压到 3–4 个；再加"已知离线集合跳过 + 补探前用更长 `-w` 重试一次"，9.5 s 可以压到 1–2 s，**不需要任何架构改动**。

## 6. 建议的落地顺序（相对报告的调整）

比报告更靠前的低成本项（都属于"阶段 0.5"，风险低、可单独验证、不碰设备行为）：

1. **接口层禁止"未连接却给值"**（N1）——换网关前必须做，否则阶段 3 会踩红线；
2. **`-w` 显式化并纳入基线测量**（§2.3、§5）：先测出现场"健康通道建立连接"的耗时分布，再定 `-w`；补探用的 `-w` 与常规读取可以不同；
3. **补探收敛**：已知离线集合不参与常规批量；失败分组先做一次"更长 `-w` + 单路"确认，再决定是否二分；
4. **写入操作总截止时间 + 操作状态可查询**（N2、N9）；
5. **全局子进程上限 + 区分"进程未启动"与"结果未知"**（N3）；
6. **单路 `read()` 复用离线退避与命令预算**（N4）；
7. **缓存失效只针对被写信号**（N5）；
8. **状态区分：不可达 / 不可解析 / 未知**（N7）。

之后按报告阶段 1→2→（可选）3→4 推进；报告阶段 0 的指标清单建议补三项：**每次快照的命令数与补探层数、`-w` 实际取值、单路 read 与 snapshot 分别统计**（否则两类读取的延迟会被混在一起）。
