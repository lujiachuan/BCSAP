# PV 读写延迟与稳定性改进报告

> 文档状态：复审修订稿（阶段性实施与待验证项目并列）  
> 编制日期：2026-09-24；复审日期：2026-09-28  
> 适用范围：桌面客户端、仪器执行服务、EPICS Channel Access 访问层，以及手动控制、扫谱、自动调束涉及的 PV 读写链路

## 1. 执行摘要

当前 PV 访问方案的核心取舍是：生产环境固定通过外部 `caget/caput` 命令访问 IOC，每次读取或写入都启动独立进程，不持有长期 Channel Access 连接。

这一方案的主要优点是故障边界清晰：某一次命令卡住或连接状态异常时，进程超时退出，下一次操作可从新进程重新发现通道，不容易把损坏的 CA 上下文长期留在执行服务内。结合写前读取、边界校验、斜坡限速、写后回读、设备组互斥和状态未知保护，当前系统在“避免错误写入”方面是偏保守的。

当前方案在本地模拟 IOC 的全在线快照约为 p95 137 ms，健康路径已有较好的正常延迟；真实控制网仍需实测。主要问题是延迟长尾和异常路径：

- 正常读取要承担进程创建和 CA 通道发现成本；
- 一路离线 PV 可能使批量读取进入二分补探，单次快照最长 20 秒；
- 写入至少包含写前 `caget`、一个或多个 `caput`、写后 `caget`；
- UI 快照与 `caput` 共用网关锁，慢快照可能阻塞写入；
- 斜坡写入每一步都会再次启动 `caput`，通信成本与安全等待叠加；
- 已有现场记录表明，连续运行到第 68 轮时出现过单次 `caput` 触及 3 秒超时。

综合判断如下：

| 维度 | 当前评价 | 说明 |
|---|---|---|
| 写入安全边界 | 较好 | 有写前真实值、边界、单步、速率、设备组锁和状态未知保护 |
| 功能正确性 | 较好 | 关键读写、批量、幂等和锁路径已有自动化测试 |
| 正常读取效率 | 本地模拟 IOC 较好，现场待测 | 128 路全在线批量快照 p95 137 ms；该数字不能外推到现场 |
| 延迟可预测性 | 一般 | 正常值与离线/超时场景的长尾差距可达一个数量级 |
| 长时间连续运行 | 中等 | 独立进程便于自愈，但累计进程启动和重复建连会引入偶发抖动 |
| 可观测性 | 偏弱 | 已增加健康快照总耗时并将误导性的逐项 `latency_ms` 留空；锁等待、进程数、阶段耗时和 p95/p99 仍缺失 |
| 故障恢复 | 中等偏好 | 离线隔离和调束写后确认有效，但恢复可见性和通用幂等仍有缺口 |

建议先处理断线读数安全、读写幂等、手动页按需读取和补探长尾，再建立现场基线。持久 CA 子进程是条件性备选项：只有现场耐久数据证明进程创建或重复建连仍是瓶颈时才启动。

## 2. 评估边界与证据说明

### 2.1 本次评估覆盖

本报告覆盖以下路径：

1. 手动控制页周期性读取全部或部分受控信号；
2. 单路手动写入；
3. 成组写入；
4. 扫谱中的写入、等待稳定和目标采样；
5. 自动调束中的多变量写入、稳定判断、写入中断确认与有限重试；
6. PV 健康检查和设置页按需检测；
7. 命令行 EPICS 网关与仓库内现有长连接 CA 网关。

本报告不评价 IOC 内部处理周期、具体设备物理响应速度、控制网交换机性能，也不擅自判断现有 `max_step`、`max_rate`、`settle_tol` 是否应放宽。这些参数属于设备安全能力，需要现场设备负责人确认。

## 3. 当前架构与调用链

### 3.1 总体链路

```text
桌面客户端
  │  本机 HTTP/JSON
  ▼
instrument_service（FastAPI，单进程）
  │
  ├─ InstrumentRuntime：设备组锁、任务占用、配置热更新
  ├─ SignalWriteService：校验、斜坡、回读、稳定判断
  ▼
CommandLineEpicsGateway
  │  每次启动 caget.exe / caput.exe
  ▼
EPICS Channel Access 网络
  ▼
IOC / 实际设备
```

桌面客户端不直接访问 IOC。该边界应保留，因为设备锁、安全校验、审计和恢复策略都集中在执行服务中。

### 3.2 读取链路

手动页的读取周期为 1 秒。每次定时触发时：

1. 如果上一请求仍在飞，跳过本次触发，不叠加请求；
2. 客户端 POST `/control/v1/signals/read`；
3. 未指定信号时，执行服务解析为当前映射中的全部信号；
4. 命令行网关尝试一次批量 `caget -w 1 -n PV1 PV2 ...`；
5. 若批量输出缺少部分值，则对缺失集合做二分补探；
6. 把每路结果组装成快照返回界面。

关键参数：

| 参数 | 当前值 | 影响 |
|---|---:|---|
| 手动页轮询周期 | 1 秒 | 仅在上一请求已完成时才真正发起下一次读取 |
| 快照缓存 | 0.25 秒 | 对 1 秒单页轮询帮助有限，主要用于短时间重复调用 |
| `caget -w` 的 CA 等待 | 显式 1 秒 | 保持原命令行默认行为；现场测得健康通道建连分布后再评估调整 |
| 单个子进程的 Python 超时 | 3 秒 | 对真正卡住的命令兜底；不能当作离线 PV 的通常耗时 |
| 批量快照总截止时间 | 20 秒 | 多路离线时二分补探的总时间上限 |
| 单次快照最大命令数 | 32 | 防止全离线时展开为近似 `2N-1` 个子进程 |
| 离线重试间隔 | 10 秒 | 保护健康 PV 不被坏路持续拖慢，但恢复显示可能延迟 |
| 客户端读请求超时 | 30 秒 | 略高于服务端 20 秒快照截止时间 |

### 3.3 单路写入链路

一次普通写入的实际步骤为：

1. 客户端建立新的 `command_id`；
2. 客户端全局写闸门确保当前桌面进程只有一个写请求在飞；
3. 执行服务按设备组申请锁；
4. 校验信号可写性、数值有限性和上下限；
5. 用单路 `caget` 读取设备真实当前值；
6. 根据 `max_step` 计算斜坡步数；
7. 根据 `max_rate` 计算步间等待；
8. 每一步分别启动一次 `caput`；
9. 写完后优先读取 `readback_signal`，没有时读取设定信号本身；
10. 返回请求值、原值、实际下发值、斜坡步和立即回读。

手动页收到“已下发”不等于设备已经稳定。设备是否进入容差由后续快照展示；扫谱和调束则显式调用 `wait_settled`，默认每 0.2 秒读取一次回读，直到到位或超时。

### 3.4 成组、扫谱和调束

- 成组写入的“原子”含义是整批先干跑校验；正式下发仍是逐路执行，途中设备故障仍可能部分成功；
- 扫谱启动前检查本次实际需要的设定、回读和探测信号，不要求全系统所有 PV 都在线；
- 扫谱逐路写入，再逐路等待回读进入容差；
- 自动调束写入失败时会回读判断设备位于目标、原位还是未知位置；只有确认仍在原位时才允许有限重试；
- 扫谱、调束和当前修订后的手动写入在设备状态未知时保留设备组锁，等待人工确认。

`command_id` 由手动单点请求携带；扫谱、调束和回落内部构造的写入请求通常没有它，依赖任务状态机与回读判断。成组接口的客户端写入项也未统一附带命令号，不能把单点幂等能力宣称为全链路保证。

这些策略应保留，不应为了降低延迟而绕开。

## 4. 延迟模型

### 4.1 快照读取

一次快照的近似耗时可表示为：

```text
T_snapshot = T_queue + Σ(T_process_start + T_CA_discovery + T_get + T_parse)
```

全部 PV 在线、批量命令正常返回时，求和项通常只有 1 项。存在坏路且批量命令不返回任何成功值时，会进入二分补探，最多 32 项，但同时受 20 秒总截止时间限制。

本地模拟 IOC 的 128 路中 1 路离线：首次二分补探用了 15 个命令、约 9.5～9.7 秒；之后 10 秒隔离窗内只读健康集合，约 76～160 ms；隔离到期的单路重探约 1.21 秒。20 秒是多路失败等更坏情形的截止时间，不是每次离线快照都会耗满的时间。`T_queue` 还包括其他页面和任务的并发请求，当前服务端没有明确的全局等待上限。

手动页实际刷新周期不是固定 1 秒，而是：

```text
T_refresh ≈ max(1 秒, T_snapshot)
```

原因是页面不会并发堆积快照。该策略能保护服务，但意味着一次慢读会直接拉长整页数据年龄。

### 4.2 单步写入

不需要斜坡时：

```text
T_write_1 = T_group_lock
          + T_pre_read_caget
          + T_gateway_wait
          + T_caput
          + T_post_read_caget
          + T_HTTP
```

Python 对每个外部命令设 3 秒兜底；`caget` 的 CA 等待显式为 1 秒。本地模拟 IOC 的离线单路 `caget` 约 1.07 秒，单步写入约 344 ms。两个数字都不是现场保证值；也不能把三个兜底超时相加当作正常离线耗时。

`T_gateway_wait` 需要特别关注：`caput` 与快照共用 `_snapshot_lock`。如果写入发生时快照正在做离线补探，首个 `caput` 可能等待接近整个 20 秒快照截止时间。

### 4.3 斜坡写入

斜坡步数和步间等待为：

```text
N = ceil(abs(target - previous) / max_step)
T_step_delay = step_size / max_rate
```

总耗时近似为：

```text
T_write_ramp = T_pre_read
             + Σ(每步 caput)
             + (N - 1) × T_step_delay
             + T_post_read
             + 快照插队或锁竞争时间
```

需要区分两类耗时：

- `T_step_delay` 是有意设置的设备安全等待；
- 每一步的进程启动与 CA 建连是架构开销。

SIM 报告中 87 次写入累计 41.13 秒，而稳定等待接近 0。该结果证明在当前设备档案下，大跨度多变量动作可能主要受 `max_step/max_rate` 限制；由于 SIM 不经过真实 `caget/caput`，它不能衡量生产通信开销。

典型安全等待示例：

- 主高压电流设定：`max_step=10`、`max_rate=100/s`，50 步约有 4.9 秒步间等待；
- 磁铁电流设定：`max_step=100 A`、`max_rate=50 A/s`，3 步约有 4 秒步间等待；
- DW 电压：`max_step=500 V`、`max_rate=5000 V/s`，每个步间约 0.1 秒。

因此“调低轮询间隔”不能解决这部分耗时；只有设备能力确认后调整档案，或使用设备自身受控斜坡功能，才可能安全降低。

## 5. 稳定性分析

### 5.1 已具备的安全能力

#### 写入前置校验

- 只读部署统一拒绝所有写入；
- 信号级可写性校验；
- 非有限数拒绝；
- 最小值、最大值校验；
- 基于现场当前值计算单步变化；
- 超大斜坡步数上限为 128，避免一次请求无限执行。

#### 并发与资源隔离

- 手动写入会短暂占用设备组；
- 扫谱和调束持有所需设备组，其他操作不能穿透；
- 成组动作先一次性申请全部分组，避免拿到一半后等待；
- 状态未知时保留设备组锁，要求人工确认。

#### 失败语义

- 写命令异常后不会假装设备未动作；
- 结果包含 `device_state_unknown`；
- 调束路径通过回读区分“目标已生效”“仍在原位”“位置不明”；
- 只有确认在原位时才允许有限重试；
- 回退和收尾同样执行回读确认。

#### 读取降级

- 一路失败不阻断其他读数返回；
- 离线 PV 隔离 10 秒，避免每秒重复拖慢健康信号；
- 批量补探有命令数与总时间硬上限；
- 页面不堆积在飞读取。

### 5.2 主要风险

| 编号 | 风险 | 可能性 | 影响 | 当前控制 | 建议优先级 |
|---|---|---:|---:|---|---:|
| R1 | 慢快照阻塞 `caput` | 中 | 高 | 20 秒总截止时间 | P0 |
| R2 | 斜坡步骤之间被快照插入，动作被额外拉长 | 中 | 中到高 | 单次命令锁 | P0 |
| R3 | 写前读取与真正写入之间等待过久，当前值可能变旧 | 低到中 | 高 | 设备组锁只能阻止本服务同组任务，不能阻止外部控制端 | P0 |
| R4 | 同一 `command_id` 的“状态未知”结果未缓存，重放可能再次写入 | 低 | 高 | 客户端通常不自动重试 | P0 |
| R5 | 两个相同 `command_id` 并发到达时都可能通过缓存检查 | 低 | 高 | 桌面客户端写闸门；外部调用方不受其约束 | P0 |
| R6 | 客户端超时后，服务端同步操作可能继续执行 | 低到中 | 高 | 设备组锁继续由服务端持有；界面可能误以为请求已结束 | P0 |
| R7 | 健康检查逐项 `latency_ms` 不代表实际 PV 延迟 | 高 | 中 | 无 | P0 |
| R8 | 命令行网关没有 IOC 原始时间戳，趋势时间接近接收/组装时间 | 高 | 中 | 页面显示滞后提示 | P1 |
| R9 | 离线 PV 恢复后最长约 10 秒才重试 | 中 | 中 | 保护其余 PV 读取 | P1 |
| R10 | 每步启动独立 `caput`，长时间任务累计进程和建连次数很高 | 高 | 中 | 单命令超时可自愈 | P1 |
| R11 | 直接启用现有长连接网关后，超时任务无法取消，可能晚到执行 | 中 | 高 | 当前生产未启用该网关 | 保持禁用，待重构 |

#### R1/R2：快照与写入竞争

`snapshot()` 在整个批量读取和二分补探期间持有 `_snapshot_lock`。`write()` 获取同一把锁后执行一条 `caput`，但斜坡整体没有持锁。

这会形成两种长尾：

1. 写入开始时已有慢快照，首个 `caput` 等待快照完成；
2. 多步斜坡的两步之间，页面快照抢到锁并执行长补探，下一步被额外延迟。

第二种情况不仅影响用户感受，还会改变实际斜坡时间形状。延长通常比加速安全，但会造成任务耗时不可预测，并增加客户端超时概率。

#### R3：写前值陈旧窗口

安全校验基于写前单路 `caget`。该读取本身没有进入快照锁；读取结束后，首个 `caput` 可能等待慢快照。在等待期间，如果还有 LabVIEW、独立命令行工具或其他 IOC 客户端修改了设备，斜坡规划依据就可能变旧。

设备组锁只能协调本执行服务内部的任务，不能约束外部控制端。因此，应让“安全写前读取—规划—首个写入”成为同一高优先级 I/O 事务，至少不能被低优先级健康快照长时间隔开。

#### R4/R5：幂等边界

复审前，服务只把 `accepted=True` 的结果放进幂等缓存。普通拒绝一般不会改设备，但“写命令超时、设备状态未知”可能已经在 IOC 生效。如果调用方因响应丢失而用同一 ID 重放，该结果没有被缓存，存在再次执行的可能。本次修订已让首次结果全部进入内存缓存，并拒绝同一 ID 的不同请求内容。

复审前，“查缓存—执行—写缓存”不是同一原子区间。本次修订在执行层将它们置于同一锁保护范围。缓存仍只有最近 256 条，且未落盘；服务重启后的同一 ID、长期重放及成组/内部任务写入仍需独立设计。

当前进程内同一 `command_id` 的首次结果已冻结，并通过同一锁保护并发请求；下一步是持久化操作台账、明确跨重启查询与成组/内部任务的幂等边界。状态未知结果尤其不能自动重放。

#### R6：客户端超时不等于服务端取消

客户端基于 `urllib` 的超时只约束等待 HTTP 响应的线程。同步服务端处理通常不会因为客户端断开而自动取消。由此可能出现：

```text
客户端显示超时并释放本地写闸门
        │
        └─ 服务端仍在斜坡、等待锁或等待回读
```

同组新请求会被服务端设备锁挡住，但用户可能看到“上一次失败”与“设备仍在动作”并存。斜坡最多 128 步，若每步都遭遇接近 20 秒的慢快照并触及 3 秒子进程兜底，仅这些等待就可能接近 49 分钟，尚未计算安全步间等待；这不是实际常见耗时，却证明客户端 120 秒超时不能充当服务端总时限。回落逐路等待四台磁铁各 60 秒时，单是稳定等待上限就达 240 秒，也超过客户端 120 秒。需要操作状态查询和服务端截止时间设计。

#### R7：现有延迟字段失真

健康检查先执行完整 `gateway.snapshot()`，随后才在循环中为每个条目启动计时并取已经存在的结果。因此每路 `latency_ms` 接近 Python 字典读取和模型组装时间，不能回答：

- 哪一路连接最慢；
- 批量命令耗时多少；
- 花了多少时间等待锁；
- 执行了几次补探；
- 哪一次子进程超时。

在没有真实指标前调超时或切换后端，容易用主观感受替代证据。

### 5.3 现有长连接实现为何不能直接启用

仓库内已有 `ChannelAccessGateway`：

- CA 上下文和所有调用放在专用线程；
- 通道长期保存；
- 快照一次发起多路 `ca_array_get`；
- 读写不需要重复启动系统进程。

它具备显著降低正常延迟的潜力，但目前有一个关键风险：外部 `_submit()` 等待超时后，只是调用方停止等待，已经放入 CA 工作线程队列的任务并未取消。如果 CA 线程稍后恢复，一个写任务可能在调用方已经认定“超时”后继续执行。

因此不建议通过修改 `create_gateway()` 直接把生产后端切过去。安全的长期方案应把持久 CA 上下文放进独立子进程，由父进程实施硬超时、心跳、进程级重启和命令台账；任何结果未知的写命令都不得自动重放。

现有线程版还存在设计约束：非抢占 CA 上下文在线程空闲等待任务时不会主动推进事件；任务队列无界；`close()` 的哨兵排在队尾且只等待 5 秒；`_connected` 不因 IOC 重启复位；断线读数可携带 0.0 占位值。`FailoverEpicsGateway` 当前未进入生产工厂，也没有自动回切与重探机制，不能作为可直接启用的安全后备。

### 5.4 复审新增风险与边界

| 风险 | 复审结论 | 本次处理或后续条件 |
|---|---|---|
| 断线读数携带 `0.0` | 可能将回落到零误判稳定，也可能污染扫谱采样 | 已在信号接口将断线值归一为 `None`，并修正无容差时的稳定判定 |
| 手动单点或成组写入结果未知却释放组锁 | 后续动作可能在未知设备状态上继续 | 已保留组锁并接入人工确认；服务重启后的持久恢复记录仍需设计 |
| 子进程创建失败被标成设备状态未知 | 容易造成误诊和无谓人工确认 | 已区分“未启动”与“已启动但结果未知”，并限制全进程并发子进程数 |
| 离线单路读无限重复 | 稳定等待期间可连续启动大量 `caget` | 稳定等待中的读失败增加退避；安全读不使用离线缓存，恢复后仍可重探 |
| 成组干跑在设备组锁外 | 校验和下发之间可能插入本服务的其他任务 | 已把设备组锁提前到干跑之前；仍有双次预读成本，外部控制端也不受本服务锁约束 |
| 批量写入途中结果未知仍继续下一路 | 扩大部分执行范围 | 已停止后续下发，逐项标明“未继续下发” |
| 不可解析数值与不可达混淆 | 类型错误可能反复进入离线退避 | 已在命令行网关区分非数值响应并延长该类重探间隔；配置级信号类型检查仍待补充，字符串/波形 PV 不适合当前数值协议 |
| 多页面并发快照共用大锁 | 服务端等待时间没有明确上界 | 需阶段 2 的准入、合并和优先级调度 |
| 成组回落可超过客户端超时 | 界面报超时而设备仍在动作 | 需异步操作状态查询；不能单靠增大 HTTP 超时 |

评审中“长尾唯一来自二分补探”的断言范围过大：本地模拟 IOC 的首轮离线快照确实主要受补探影响，但真实现场还存在安全斜坡、设备物理响应、锁竞争、IOC 抖动与控制网故障。`-w 0.3` 在模拟 IOC 能缩短离线探针，尚不能证明现场不会误判慢连接。`-w` 的缩短应以真实控制网的健康通道建连分布为前提。

## 6. 改进目标

### 6.1 原则

1. 不降低现有边界、单步、速率、稳定容差和人工确认要求；
2. 不以并行写设备换取表面速度；
3. 不把客户端超时当作设备未动作；
4. 不自动重试状态未知的写入；
5. 安全校验读取必须使用现场值，不允许使用 UI 缓存；
6. UI 监视读取可以使用带年龄标记的短缓存；
7. 先建立基线，再确定最终超时与 SLO。

### 6.2 建议 SLO

以下为完成基线采集后需要确认的初始目标：

| 指标 | 当前已知 | 现场验收建议 | 备注 |
|---|---:|---:|---|
| 全在线、页面所需 PV 快照 p95 | 本地模拟 IOC 全量 137 ms | 先取现场基线，再设改善门槛 | 不能把模拟值当现场 SLO |
| 手动页健康数据年龄 p95 | 尚未测量 | ≤ 1.5 秒 | 包含 1 秒轮询相位，慢快照单独统计 |
| 设备组锁冲突拒绝率 | 尚未测量 | 按真实操作负载定目标 | 当前冲突即拒绝，服务端没有设备组等待队列 |
| I/O 调度等待 p95 | 当前未单独计量 | 阶段 2 完成后设定 | 与设备组锁冲突分开计量 |
| 单步写入请求完成 p95 | 本地模拟 IOC 约 344 ms | 现场基线后确定 | 不含设备物理稳定 |
| 写入因普通监视快照额外等待 | 当前可能接近慢快照总耗时 | 阶段 2 不超过当前单条命令 | 需故障注入证明 |
| 已判离线 PV 的恢复发现 | 当前约 10 秒退避 + 探针 | 可见关键路目标 ≤ 3 秒 | 必须先实现分类退避；当前版本不能满足 |
| 同一 `command_id` 重复设备写入 | 当前只对内存缓存窗口内的单点写有保障 | 0 次 | 跨重启、成组及内部任务需独立台账 |
| 8 小时连续运行未知写入 | 未测量 | 0 次 | 必须现场耐久测试 |

“单步写入完成”只代表命令成功下发并完成立即回读，不等于设备进入稳定容差。稳定时间应单独记录。

## 7. 分阶段改进方案

### 7.1 阶段 0：建立真实基线与可观测性

目标：不改变设备行为，只回答“时间花在哪里”。

建议为每个读写操作生成 `operation_id`，记录：

- 操作类型：快照、单读、单写、斜坡写、稳定轮询、健康检查；
- 请求信号数、在线数、离线数；
- 队列等待时间；
- 网关锁等待时间；
- 外部进程数量；
- 每个外部进程的命令类型、耗时、返回码和是否超时；
- 快照总耗时和补探层数；
- 每次快照的命令数、`-w` 实际取值，以及单路 `read()` 与批量 `snapshot()` 分开的耗时分布；
- 写前读、每步写、步间安全等待、写后读、稳定等待的分段耗时；
- 是否命中缓存、是否命中离线退避；
- 操作结束时的状态：成功、拒绝、离线、超时、状态未知。

健康接口建议调整语义：

- 报告一次快照的 `total_latency_ms`；
- 每路只报告连接状态、值、数据年龄和失败原因；
- 不再把批量结果组装时间标成单路 PV 延迟；
- 如确需单路诊断延迟，应由设置页显式发起单路测试，不混入正常全量健康检查。

建议至少采集以下基线：

1. 全部在线，连续读取 10 分钟；
2. 1 路离线、10% 离线、全部离线；
3. 离线恢复；
4. 手动页轮询期间执行单步写；
5. 手动页轮询期间执行 10 步斜坡；
6. 扫谱和调束各连续运行 8 小时；
7. 控制网有重复 PV 名或错误地址时的表现。
8. 映射到非数值字符串、枚举或波形 PV 时的错误分类；
9. 多页面同时读取、慢快照与写前单读/回读稳定轮询竞争时的等待时间。

阶段 0 验收：能从一条操作日志中还原总耗时，以及每一段等待属于进程、网络、锁、安全斜坡还是设备稳定。

### 7.2 阶段 1：低风险减少无效读取

### 只读取页面实际使用的信号

手动页当前未传 `signals`，因此读取整份映射。建议改为页面当前实际展示的设备信号，加上：

- 顶栏读数；
- 趋势信号；
- 可写信号对应的回读信号；
- 开关和模式状态；
- 当前可见卡片所需的附属读数。

设置页保留“当前可见行检测”；初始化健康检查仍可以全量执行，但不应与高优先级写入竞争。

收益：隐藏或未使用的离线 PV 不再拖慢操作页；读取负载随当前任务规模而不是全系统映射规模增长。

风险：漏掉一个 UI 依赖会造成字段不刷新。需要由页面设备规格统一生成信号集合，并增加“页面引用的信号全部被请求”测试，避免手写清单漂移。

### 区分当前值、最后成功值和数据年龄

建议 UI 不用失败结果覆盖最后成功值，而是同时显示：

- 最后成功值；
- 最后成功时间；
- 当前连接状态；
- 数据年龄；
- 超过阈值后明确标记“陈旧”，禁止把旧值用于安全判断。

这可以减少偶发读失败造成的数字闪空，同时不掩盖掉线。

### 修复通用幂等

建议：

1. 同一 `command_id` 第一次到达即登记为“执行中”；
2. 后续相同请求等待或查询首次结果，不再执行；
3. 成功、普通拒绝、状态未知全部形成不可变结果；
4. 同一 ID 但请求内容不同，直接拒绝并记录协议错误；
5. 幂等台账至少覆盖客户端最大重试/查询窗口，关键写入可落盘。

阶段 1 验收：一个未展示的离线 PV 不再影响手动页；同一命令 ID 在同一执行服务进程的缓存窗口内最多写设备一次。跨重启与成组/内部任务需要持久操作台账，不能由内存缓存验收代替。

### 7.3 阶段 2：建立统一、有优先级的 I/O 调度器

目标：消除低优先级监视读取对控制写入的长时间阻塞，同时避免无序并发访问 CA 网络。

建议所有命令行 EPICS 操作进入单一调度器：

| 优先级 | 操作 |
|---:|---|
| 0 | 状态未知确认、保护性回退、紧急停止相关写入 |
| 1 | 已批准的手动/扫谱/调束写入及其安全写前读、写后确认 |
| 2 | 正在运行任务的稳定判定和目标采样 |
| 3 | 当前可见页面快照 |
| 4 | 初始化健康检查、设置页全量诊断、离线后台重试 |

关键语义：

- “安全写前读—斜坡规划—首个 `caput`”作为不可被低优先级任务打断的事务；
- 多步斜坡之间可以允许必要的高优先级安全操作，但不允许普通全量快照插入；
- 二分补探每执行一个 `caget` 分组后重新让出调度权，不持有 20 秒大锁；
- 相同信号集合的多个 UI 快照合并为一个请求；
- 队列有容量上限，旧的未执行 UI 快照可被更新请求替换；
- 写操作绝不因队列合并而丢弃或重排；
- 增加公平性控制，防止持续写入使监视永久饿死。

调度器解决的是排队与竞争，不改变 `max_step/max_rate`。

阶段 2 验收：离线补探进行中发起写入，写入最多等待当前一条外部命令结束，不等待整个 20 秒快照；斜坡步骤间不再被普通页面快照插入。

### 7.4 阶段 3：条件性评估独立进程中的持久 CA 会话

触发条件：阶段 0～2 完成后，真实控制网耐久测试仍证明进程启动/重复建连对正常路径或故障率构成主要瓶颈。若健康路径维持本地模拟 IOC 观察到的百毫秒量级且长尾已收敛，本阶段不实施。

建议架构：

```text
instrument_service（业务与安全边界）
  │
  │ IPC：带 request_id / command_id / deadline
  ▼
epics_worker 子进程
  ├─ 单一 CA 上下文线程
  ├─ 持久通道
  ├─ 批量 get / put
  ├─ 连接状态和订阅缓存
  └─ 心跳
        │
        ▼
       IOC
```

父进程职责：

- 保存设备锁与幂等台账；
- 对每个操作设硬截止时间；
- 心跳失效时终止并重建 worker；
- worker 重启后先恢复读通道，不自动重放任何结果未知写入；
- 明确区分“请求尚未发给 CA”“已发但无确认”“已确认完成”。

worker 职责：

- 所有 CA 调用在同一专用线程执行；
- 持久保存通道和连接状态；
- 使用 IOC 时间戳和 severity；
- 批量读取；
- 接收到父进程取消时，只取消尚未提交到 CA 的读任务；已提交写入不能伪装取消成功。

上线顺序：

1. 影子读取：命令行结果用于业务，长连接只旁路读取并比较；
2. 读取切换前验证断线值在信号接口层变成 `None`，并以状态、时间戳和数值对齐通过影子测试；写入仍用 `caput`；
3. 小范围写入：先选低风险模拟 IOC/非关键设备；
4. 全量写入：经过耐久、断网、IOC 重启和 worker 卡死测试后再启用；
5. 命令行工具保留为人工诊断通道，不在状态未知写入中自动切换后端重试。

阶段 3 验收：worker 卡死可被父进程回收；任何写入最多执行一次；IOC 重启后通道自动恢复；8 小时运行无队列累积和未知晚到写入。

### 7.5 阶段 4：设备级节拍优化

只有在阶段 0 的数据证明主要耗时确实来自安全斜坡，并取得设备负责人书面确认后，才评估：

- 放宽特定设备的 `max_step`；
- 提高特定设备的 `max_rate`；
- 使用磁铁电源自身的速率设定 PV，由设备控制器执行平滑斜坡，应用只下发一次目标；
- 调束先采用逐参数阶段，再进入联合微调，减少每轮同时变化的路数；
- 成组设备在硬件支持时采用设备侧同步触发，而不是应用层并行 `caput`。

每项变更都必须分别验证过冲、跟随误差、掉线行为、急停、回退和稳定判据。不能因为软件显示“更快”就修改安全参数。

## 8. 不建议采用的捷径

### 直接把单命令超时从 3 秒降到 1 秒

这会把网络抖动转化为更多“设备状态未知”，不能减少已经发出的命令风险，反而增加人工确认和重试压力。

### 直接提高快照缓存时间

缓存能降低读取次数，但会增加数据年龄。若没有明确标注年龄，操作员容易把旧值当作当前值。安全写前校验更不能使用 UI 缓存。

### 直接启用现有 `ChannelAccessGateway`

现有实现的超时不会取消 CA 工作线程中的任务。尤其对写入而言，存在“调用方已超时、后台稍后执行”的风险。

### 并发执行多个 `caput`

并行可能降低表面耗时，但会破坏跨设备顺序、斜坡约束和部分失败可解释性。除非硬件提供受控同步机制，否则不建议。

### 自动重试所有写入超时

超时不等于未执行。只有可靠回读证明设备仍在原位时才允许重试；读不到或位于中间位置必须停止并人工确认。

### 未经设备确认放宽 `max_step/max_rate`

这部分时间是安全约束，不属于纯软件性能损耗。

## 9. 验证方案

### 9.1 功能与故障注入矩阵

| 场景 | 应验证结果 |
|---|---|
| 全部 PV 在线 | 单次批量读取；数据完整；达到快照 SLO |
| 1 路隐藏 PV 离线 | 当前页面刷新不被拖慢 |
| 1 路可见 PV 离线 | 其他值继续更新；坏路明确标记；恢复在目标时间内发现 |
| 10% PV 离线 | 补探命令数和总时间受限；写入优先级不受影响 |
| 全部 PV 离线 | 不产生进程爆炸；20 秒内返回；服务可继续响应状态接口 |
| 快照中发起单步写 | 写入不等待整个快照；安全写前值在限定时间内有效 |
| 快照中发起斜坡写 | 普通快照不插入斜坡步骤之间 |
| `caput` 返回前客户端断开 | 服务端状态可查询；不允许用户误判为未执行 |
| `caput` 已执行但响应丢失 | 回读到目标则确认成功；不重复写入 |
| 回读仍在原位 | 在配置允许时有限重试 |
| 回读位于中间值或不可读 | 状态未知；保留锁；不自动重试 |
| 同一 ID 串行重放 | 返回首次结果，不写第二次 |
| 同一 ID 并发提交 | 只有一个实际执行者 |
| 同一 ID 不同内容 | 拒绝并记录协议错误 |
| IOC 重启 | 读通道恢复；未知写不自动重放 |
| CA worker 卡死 | 父进程终止并重建；业务服务不永久阻塞 |
| 外部控制端在写前读后改值 | 写事务重新确认或拒绝陈旧规划 |

### 9.2 耐久测试

建议最少进行：

- 8 小时全在线持续轮询；
- 8 小时混合在线/离线持续轮询；
- 1000 次单步写入，覆盖不同设备组；
- 100 次多步斜坡，记录实际步间隔；
- 100 次响应丢失/超时故障注入；
- 50 次 IOC 重启或网络短断；
- 20 次 CA worker 强制卡死与重建。

输出至少包括 p50、p95、p99、最大值、超时率、每操作平均子进程数、锁等待占比、离线恢复时间和未知状态次数。

### 9.3 安全验收红线

出现以下任一情况不得上线：

- 同一 `command_id` 导致两次实际写入；
- 状态未知写入被自动重放；
- 客户端超时后出现未记录的晚到写入；
- 页面缓存被安全校验路径使用；
- 设备组锁可被手动、扫谱或调束绕过；
- 回读未稳定却被记录为有效扫描点；
- worker 重启后自动补发重启前未知写入。

## 10. 实施优先级与预期收益

| 阶段 | 内容 | 风险 | 预期收益 | 是否依赖现场硬件 |
|---|---|---:|---|---:|
| 0 | 阶段耗时与队列指标、修正健康延迟语义 | 低 | 建立可信基线，避免盲调 | 是，最终基线需要 |
| 1 | 页面按需读取、数据年龄、进程内及持久幂等 | 低到中 | 减少无效读取，逐步收敛重复写风险 | 部分 |
| 2 | 有优先级的统一 I/O 调度器 | 中 | 显著收敛写入等待长尾 | 是 |
| 3（条件触发） | 独立进程持久 CA 会话 | 中到高 | 仅在现场证明进程/建连仍是瓶颈时实施 | 强依赖 |
| 4 | 设备档案和硬件斜坡优化 | 高 | 降低物理动作节拍 | 必须 |

建议的近期交付边界是阶段 0～2。它们不要求改变设备安全参数，也不要求立即替换 EPICS 后端，就能解决“看不清耗时”“无关坏路拖慢页面”“慢快照阻塞写入”和“通用幂等不完整”四个核心问题。

阶段 3 只有达到触发条件才作为独立项目推进，使用影子读取和灰度写入。阶段 4 必须由软件、设备和现场运行负责人共同评审。阶段 0～2 也仍需分批完成，不能以本次安全修复代替全部验收。

## 11. 建议决策

建议批准以下方向：

1. 保留执行服务作为唯一硬件写入口；
2. 保留现有安全校验、设备组锁、状态未知和人工确认语义；
3. 先建设真实耗时指标并完成现场基线；
4. 手动页改为按实际展示信号读取；
5. 补全 `command_id` 在飞与终态幂等；
6. 用统一优先级调度替代整段快照大锁；
7. 如现场数据证明必须引入长连接 CA，再采用独立子进程方案；
8. `max_step/max_rate` 的任何调整单独走设备安全评审。

在完成阶段 0 基线前，不承诺具体毫秒级收益。阶段 1、2 优先改善离线补探和锁竞争长尾；阶段 3 的投入取决于届时现场剩余瓶颈。

## 12. 本报告结论

当前实现不是“不稳定”，而是采用了“每次新进程换取故障自愈”的保守方案。它对单次连接污染有较强隔离能力，也具备较完整的设备安全语义；问题集中在重复建连成本、离线补探长尾、读写调度不分优先级、通用幂等边界和可观测性不足。

最合理的改进路径不是立即更换通信库，而是：

```text
真实测量
  → 缩小监视读取范围
  → 补全幂等
  → 建立写优先的统一调度
  → 现场仍有进程/建连瓶颈时才评估持久 CA
  → 经设备确认优化物理斜坡
```

该顺序可以在不削弱安全性的前提下，先收敛最影响操作体验的长尾，再逐步降低正常路径延迟。

## 13. 复审后执行记录与未完成边界（2026-09-28）

依据《PV读写延迟与稳定性改进报告-评审意见》，本次仅实施可在现有架构内验证、且不改变现场安全参数的修正：

| 已实施 | 具体边界 |
|---|---|
| 断线值安全 | 信号接口对 `connected=False` 一律返回 `value=None`；无稳定容差时仍要求回读可读，避免断线占位 `0.0` 被当成真实值 |
| 写入结果保护 | 同一进程内同一 `command_id` 的首次结果（含拒绝和状态未知）被缓存，同 ID 不同请求被拒绝；手动单点和成组状态未知会保留设备组锁，待人工核对后释放；成组写入遇状态未知停止后续成员 |
| 子进程与读取 | 命令行网关全进程最多 8 条并发命令；显式 `caget -w 1`，没有缩短现场建连窗口；只把可确认的进程创建失败判为“未下发”；非数值响应与离线分开，避免对此类 PV 继续二分补探；稳定等待的单路读失败退避至最多 2 秒 |
| 页面与健康检查 | 手动页只请求当前展示所需信号；成组和全部关断的未知状态结果会刷新人工确认入口；健康检查新增整次快照耗时，旧逐路耗时无可信逐项测量时留空 |

本次**没有**承诺真实现场延迟改善数值，也没有完成阶段 0～2：

- 尚无真实控制网的 p50/p95/p99、掉线恢复和长时间运行基线；本地模拟 IOC 的 137 ms 不能外推。
- 手动未知状态的人工确认记录与命令幂等缓存目前均在进程内；执行服务重启后缺少持久台账。上线前应设计重启恢复与不可自动重放的操作状态查询。
- 写入整体服务端截止时间、超时后状态查询、成组回落与客户端超时的一致性尚未实现；仅凭客户端超时不能判断设备未动作。
- 低优先级快照仍可能持有整段网关锁，写优先调度和阶段耗时/队列指标仍需阶段 0～2 单独实施。
- 未改动 `max_step`、`max_rate`、稳定容差、`-w` 的现场数值，也未启用现有线程版 CA 网关或自动故障切换。

建议先在真实控制网只读测量，再评审持久操作台账与统一 I/O 调度的接口和故障语义；任何生产灰度写入都需设备负责人确认。

本次验证使用仓库 `.venv` 的 Python 3.12.14、pytest 9.1.1。PV 网关、信号写入、成组写入、手动页相关新增场景和初始化健康检查的定向回归为 **97 passed**。扩展到整个手动页 `PageTests` 时曾得到 **111 passed、1 failed**；失败项是 `test_topbar_falls_back_to_a_panel_when_there_are_too_many_readouts` 的卡片布局数量断言（预期 4、实际 0），与本次 PV 通信路径不重合，未在本次改动中修复。上述测试均不代替真实 IOC 联调和长时间运行验证。
