### 1.2 真实线格式：无换行、无长度前缀、连续拼接的"完整前缀数组"

- 无换行/无分隔符：6615 条原始采样里含 `\r`/`\n` 的为 0 条。**【代码证实】**（`raw_debug.log`）
- 单次 `recv` 可含多个数组：276/6615 条出现 `][`。**【代码证实】**
- 帧的增长形态：`[]` → `[{第0点}]` → `[{第0点},{第1点}]` …… 即**从扫描起点到当前点的完整前缀数组**，扫描间隙发 `[]`。**【代码证实】**（`raw_debug.log:253`）
- 全量重发：16:56:42–17:08:40 内 664 次数组起点的首点 X 只有 3 个不同值（如 `25.863697…` 出现 282 次）。**【代码证实】**
- 接收端用正则抓 `"X":…,"Y":…`，块尾残片留到下一块，按**浮点 X 精确去重**（新值覆盖同 X 旧值），最后按 X 升序输出。**【代码证实】**（`labview_listen.py:36-37,39-72,183,83,94`）

## 2. 冻结规则一：帧协议

**优先与 LabVIEW 端约定应用层帧**，按推荐顺序：

1. **4 字节网络序长度前缀 + UTF-8 JSON**（首选：帧边界明确，解析器无需猜）；
2. 每帧一行 NDJSON（次选：LabVIEW 侧写起来略别扭，但同样明确）；
3. **仅当 LabVIEW 端无法修改时**：接收器实现**增量 JSON 数组解析**，把"每次完整数组"当作一帧——绝不允许再用正则在全缓冲区里捞 `"X"/"Y"`。

> 判定：旧方案的根因不是正则不够聪明，而是**字节层没有帧边界**，却想从字节层推断语义。方案 3 也必须把数组边界真的解析出来（括号配对 + 字符串转义处理），而不是"看起来像一帧"。

### 2.1 每帧字段（冻结）

```json
{
  "protocol_version": 1,
  "run_id": "MS-20260914-001",
  "frame_seq": 37,
  "sent_at": "2026-09-14T10:30:21.123+08:00",
  "axis": "dipole_current",
  "detector": "picoammeter",
  "units": {"x": "A", "y": "nA"},
  "full_snapshot": true,
  "point_count": 1520,
  "points": [
    {"index": 0, "x": 40.0, "y": 0.012, "sampled_at": "2026-09-14T10:30:20.900+08:00"}
  ],
  "checksum": "<对 points 规范化序列化后的 sha256>"
}
```

字段语义（**冻结，不再变**）：

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| `run_id` | 扫描批次唯一标识，由**接收端在 ARMED 时生成下发给 LabVIEW**（或由 LabVIEW 生成后首帧上报，二选一，接入前定） | 只能继续靠 X 回跳猜批次 → 同起点/更高起点/反向扫描会混批 |
| `frame_seq` | 单调递增帧号，识别重复/乱序/缺失 | 无法判断"是否收到过完整序列"，也无法做断线补齐 |
| `point.index` | 采集顺序，允许反向扫描与重复坐标 | 按 X 排序会丢时间顺序 |
| `full_snapshot` | 这帧是完整快照还是增量点 | 无法区分"补齐"与"新增" |
| `point_count` + `checksum` | 发现截断/损坏/不完整终帧 | 终帧不完整也看不出来 |
| `sent_at` + 接收端 `received_at` | 审计时间用带时区时间戳；顺序/超时判断用单调时钟 | 时间不可比 |

### 2.2 校验与限额（冻结）

- 所有数值必须有限（拒绝 NaN/Inf）；`x`/`y` 不得为字符串；
- 单帧字节上限、最大点数、字段长度上限必须配置，超限只记录错误并丢弃该帧，**不能拖垮接收服务**；
- `checksum` 校验失败：**保留上一个已确认版本**，不合并、不覆盖；
- 未知 `protocol_version`：拒绝并明确报错，不做"尽量解析"。

## 3. 冻结规则二：批次标识

- 一个活动批次只有**一个** `run_id`；由接收端在 `ARMED` 阶段确定并记录到任务元数据（`scan_runs.meta_json` 或专用列）。
- **禁止**用 X 值、点数、时间间隔推断批次（旧实现的三条推断路径全部废止：3 A 回跳、`labview_reset.flag`、GUI 清空）。
- `labview_reset.flag` 一类的"人工清空"只允许映射为**显式的新批次命令**（写 `run_id` / 调用接收端接口），不允许直接改内存剖面。
- 同一 `run_id` 重复收到全量帧：允许（用于补齐），按 `frame_seq` 取最高版本；收到**更低** `frame_seq` 的全量帧：忽略并计数。
- 收到不同 `run_id` 的连接：拒绝（除非当前没有活动批次），并记录来源与时间。

## 4. 冻结规则三：完成判据

**完成不能只依据"TCP 暂时没数据"。** 判据按优先级：

1. **明确完成 PV**：LabVIEW/MSScan 侧提供一个"采集完成/VI 结束"信号（`BD:MS:Scanz:RunVI` 的运行状态、或新增 `ScanDone` 类 PV）——
   **这是首选，接入前请现场确认是否可实现**；实现后接收器只依赖它 + 终帧完整性。
2. 若拿不到完成信号：`停止命令 + 连接状态 + 连续静默时间 + 终帧 frame_seq + 预期点数` 共同判定，并且**必须**满足"终帧校验通过"才能判 `COMPLETED`；否则 `INCOMPLETE`。

生命周期状态机（冻结）：

```text
IDLE → ARMED → RUNNING → DRAINING → FINALIZING → COMPLETED
                         └──────────────→ FAILED / RECOVERY_REQUIRED
```

- `ARMED`：建 `run_id`、保存设备/实验元数据快照、**确认监听就绪后**才触发 MSScan；
- `RUNNING`：记录 `frame_seq`、唯一点数、最后数据时间、连接状态；
- `DRAINING`：收到停止/完成信号后继续等**最后完整帧**，不按当前快照立即收尾；
- `FINALIZING`：核对终帧点数、序号连续性、校验值、设备停止状态，**强制落盘**；
- `COMPLETED`：数据与元数据都原子发布后才对客户端可见；
- 无法确认完整性 → `INCOMPLETE`/`FAILED`，允许导出已恢复数据，但**不得显示为完整谱图**。

## 5. 冻结规则四：唯一事实数据源

分层（冻结）：

```text
TCP 帧 → 帧校验 → 任务内追加记录/版本化快照 → SQLite 元数据 + 点文件
       → 完成时原子发布 NPZ → UI 增量接口 → latest_labview.json（可选诊断快照）
```

- **唯一事实源是任务存储**（沿用现有 `scan_store` 的分层：SQLite 元数据 + `scan_points` 点表 + NPZ 曲线 + SHA-256）。UI 与导出都从任务存储读。
- `latest_labview.json` 只作为**可丢弃、可重建的兼容快照**，并且必须满足：
  - 单一写入者（禁止 `labview_live.py` 与监听器同时写；GUI 不得再直接覆盖/删除 `.tmp`）；
  - 同目录唯一临时文件 + `flush + fsync` + `os.replace`；**替换失败保留旧快照并报警，绝不回退为直接覆盖**；
  - 包含 `run_id`、`snapshot_seq`、唯一点数、最后点序号、生成时间、完整性校验；
  - 读取端先比 `run_id`/`snapshot_seq`，只接受更新版本；解析失败继续显示上一有效版本并提示快照异常。

## 6. 接收器要求（与规则配套，接入时逐条实现）

1. 每条 TCP 连接**独立**缓冲区与解析状态；禁止跨连接共享残片（旧实现 `_PEND` 是模块级全局，断线重连会把半截对象拼到新连接上——**【代码证实】** `labview_listen.py:39,167,217-219`）。
2. 只允许一个受信来源写一个活动 `run_id`；第二连接拒绝或进入明确的备用状态（旧实现监听 `0.0.0.0` 且无来源校验，现场日志里出现过**三个并发**连接：`labview_listen.log:82-84`）。
3. 网络读取与入库解耦：**有界队列**，队列接近上限要报警，不能静默丢点。
4. 连接中断：任务标记 `DATA_INTERRUPTED`，保留已接收点与断点序号；重连只接受同一 `run_id` 的更高 `frame_seq`；半帧必须丢弃。
5. 中继若保留：至少记录断连区间与丢弃字节数（更可靠的中继需按完整帧缓存重放，而不是转发裸字节流）。
6. 接收循环结束、收到停止、Run 完成、超时 → **必须强制落盘一次**，不能只依赖 0.5 s 定时快照（旧实现在断连/异常路径都不落盘，最后一批点会丢）。
7. 监听地址优先绑定实验网专用网卡，不默认 `0.0.0.0`；防火墙限制来源 IP；一个端口只跑一个实例，启动时检测占用并报错（**不要**强杀未知占用进程）。
8. 日志限频/聚合：不得像旧中继那样每 65536 字节写一条日志。

## 7. 界面上必须看得见的东西（可观测性）

扫谱页至少显示：当前 `run_id` 与数据来源；TCP/中继/LabVIEW/MSScan 各自状态；最后数据距今时间；最新 `frame_seq`、收到帧数、唯一点数；重复帧/乱序帧/解析失败/校验失败/断线次数；预计点数与当前完整度；当前数据是**完整 / 恢复中 / 仅部分**。

## 8. 验收测试清单（接入完成前必须全过）

沿用报告 §6.3.9，逐条落到自动化测试：

1. 同一帧按 1 字节 / 随机长度 / 65536 字节边界分包，解析结果一致；
2. 一次 `recv` 含多帧、帧头帧体被拆开时不丢帧不粘帧；
3. 连接在对象、数字、UTF-8 字符中间断开，重连后不拼出伪数据；
4. 重放相同全量帧不增加唯一点数；更高版本全量帧能补齐先前缺点；
5. 缺失/重复/乱序 `frame_seq` 必须被识别并计数；
6. 相同起点、更高起点、反向扫描、重复 X 坐标不混入上一批；
7. 扫描结束前最后一个短突发在完成前强制落盘；
8. 模拟 JSON 写中断 / 原子替换失败时，读取端仍拿到上一有效快照；
9. 同时启动两个写入器或两个 TCP 来源时必须拒绝冲突；
10. 中继断开再恢复时界面明确显示数据缺口；有全量终帧时完成补齐并通过点数与校验；
11. 接近最大点数/最大帧大小的长扫描不阻塞 UI、不无限增内存、不静默丢数据；
12. 服务或客户端在扫描中退出后，已确认点仍可恢复，任务状态明确为中断或待恢复。
